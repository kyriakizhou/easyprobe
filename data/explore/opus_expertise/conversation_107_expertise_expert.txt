HUMAN: We're implementing a distributed locking primitive using etcd. What are the edge cases we need to handle?

A: etcd locking edge cases: lease expiration while holding lock (network partition, GC pause), watch gaps (missed events during watch reconnect), and transaction conflicts. Always use fencing tokens - lock holder might not know their lock expired. Design for the lock to be advisory, not absolute.

H: How does the fencing token pattern work with etcd?

A: Lock acquisition returns revision number (monotonically increasing). Include revision as fencing token in operations. Resource checks: incoming operation's token must be >= last seen token. Stale lock holder's operations rejected because their token is old. Critical for correctness.

H: What happens when the lease expires unexpectedly?

A: Lease expires: lock released, another client can acquire. Original holder might not know immediately - still thinks it has lock. With fencing: operations fail validation. Without: split-brain - two holders operating simultaneously. Always: keep-alive must be faster than TTL, monitor for lease errors.

H: How do we implement lock with timeout using etcd?

A: Create lease with TTL, put lock key with lease. If key already exists (lock held), either fail fast or watch for deletion. Watch with timeout context. On acquire: start keep-alive goroutine. Handle: keep-alive failure (release lock), context cancellation (release lock), unexpected deletion.

H: What testing strategy catches these edge cases?

A: Chaos testing: kill processes holding locks, introduce network partitions, clock skew simulation. Linearizability testing (Jepsen-style): verify lock properties under failures. Stress testing: many clients contending. Monitor: lock acquisition time, hold time distribution, failover behavior.
