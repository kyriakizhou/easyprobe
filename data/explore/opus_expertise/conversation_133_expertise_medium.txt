HUMAN: How do I implement proper API versioning?

A: Versioning prevents breaking existing clients when you change API. Strategies: URL path (/v1/users), header (Accept: application/vnd.api+json; version=1), or query param (?version=1). URL versioning is most common and explicit.

H: When do I need a new version?

A: Breaking changes: removing fields, changing field types, renaming fields, changing response structure, removing endpoints. Non-breaking (no new version needed): adding fields, adding endpoints, adding optional parameters. Additive changes are safe.

H: How do I maintain multiple versions?

A: Options: separate code paths per version (clean but duplicated), version translation layer (single implementation, translate at boundaries), or keep old behavior with feature flags. Translation layer scales best for minor differences.

H: How long should I support old versions?

A: Define deprecation policy upfront. Communicate timeline clearly. Typical: 6-12 months support after new version. Monitor usage of old versions. Reach out to high-volume users before deprecation. Some enterprise clients may need extended support.

H: How do I communicate deprecations?

A: Documentation updates, deprecation headers (Deprecation: true, Sunset: date), changelog, direct notification to API consumers. Give ample warning. Provide migration guides. Make it easy to update.

H: What about minor changes within a version?

A: Additive changes (new fields, endpoints) can happen within a version. Document changes in a changelog. Use semantic versioning for your API if it helps (v1.2.0). Major version bump (v1 → v2) only for breaking changes.
