HUMAN: I'm setting up a development environment with Docker. Should I use Docker Compose? What about hot reloading?

A: Docker Compose is excellent for local development - define all services (app, database, redis, etc.) in one file, spin up with one command. For hot reloading, mount your source code as a volume so changes are reflected immediately without rebuilding images.

H: How do I set up the volume mounts for Node.js?

A: In docker-compose.yml, mount your source directory: volumes: ['./src:/app/src']. But there's a gotcha - node_modules should NOT be mounted from host. Use a named volume for node_modules or exclude it. Otherwise, host and container dependencies conflict.

H: Dependencies inside and outside the container could differ?

A: Yes. Some packages have native binaries compiled for specific platforms. If you mount host node_modules (developed on Mac) into a Linux container, native bindings break. Solution: docker-compose volume for node_modules that lives only in container, or install dependencies inside container only.

H: What about database data? Should it persist between container restarts?

A: Yes, use named volumes for database data: volumes: ['postgres_data:/var/lib/postgresql/data']. This survives container recreation. For development, you might also want to define volumes at the compose file level for explicit management.

H: My containers are slow to start and npm install takes forever every time.

A: Layer your Dockerfile properly. COPY package*.json first, RUN npm install, then COPY the rest of the code. Docker caches layers - unchanged package.json means cached node_modules. Also use .dockerignore to exclude node_modules, .git, etc. from build context.

H: What about differences between development and production Docker setup?

A: Use multi-stage builds. Development stage includes dev dependencies and mounts source. Production stage copies only built artifacts, uses npm ci --production, and has a minimal final image. Or use separate Dockerfiles: Dockerfile.dev and Dockerfile.prod.
