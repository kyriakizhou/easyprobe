HUMAN: I'm designing a system that needs to process exactly-once semantics for financial transactions. What are the architectural patterns to achieve this?

A: True exactly-once is theoretically impossible in distributed systems (FLP impossibility), but effectively-exactly-once is achievable through idempotency. Patterns: idempotency keys with deduplication, transactional outbox for event publishing, and two-phase commit for coordinated writes.

H: We're using Kafka for event streaming between services. How do we achieve exactly-once there?

A: Kafka has exactly-once semantics (EOS) for producers and consumers within Kafka itself. Enable idempotent producer and transactional API. Consume-transform-produce in a transaction. However, the "output" side effect (database write, external API call) still needs application-level idempotency.

H: Can you elaborate on the transactional outbox pattern?

A: Write business data and events to the database in a single transaction. Outbox table contains events to be published. Separate process reads outbox and publishes to Kafka, deleting after successful publish. If publish fails, retry from outbox. Guarantees: if business write committed, event will eventually publish.

H: How do we handle the consumer side - database write might happen twice if consumer crashes after write but before commit offset?

A: Consumer-side idempotency. Store the event ID or offset in your database along with the business data, atomically. Before processing, check if this event was already processed. Skip if yes. This makes replay safe - processing is idempotent.

H: What about external API calls? We can't make a credit card charge idempotent.

A: Payment processors support idempotency keys for exactly this reason. Send the same idempotency key on retry - Stripe returns cached response. Design your system to generate stable idempotency keys (derived from your internal transaction ID, not random per attempt).

H: How do we test exactly-once behavior?

A: Fault injection testing. Kill processes at various points, verify no duplicates or losses on recovery. Jepsen-style testing for distributed systems. Simulate network partitions, slow responses, duplicate deliveries. Count operations on both sides - they should match exactly after recovery.
