HUMAN: We're implementing a database query cache. What invalidation strategies work in practice?

A: Strategies: TTL-based (simple, stale possible), write-through (update cache on write), write-invalidate (delete cache on write), or version-based (cache with version, check on read). Choice depends on read/write ratio, staleness tolerance, and consistency requirements.

H: How do we handle cache invalidation for complex queries?

A: Complex queries touch multiple tables. Track dependencies: query → tables touched. On any table write, invalidate all queries depending on it. Over-invalidation but correct. More precise: track rows/ranges, invalidate only overlapping queries. Trade-off: tracking overhead vs invalidation precision.

H: What about caching at multiple layers?

A: Common: query result cache, prepared statement cache, buffer pool. Each layer has different invalidation needs. Coordination: lower layer invalidation should propagate up. Or: accept inconsistency between layers with TTLs. Monitor: hit rates at each layer.

H: How do we prevent cache stampede?

A: Stampede: many requests for expired key, all miss, all query database. Solutions: lock/semaphore (one request fetches, others wait), early recomputation (background refresh before expiry), or probabilistic early expiration (randomly refresh near expiry). XFetch algorithm combines these.

H: What metrics indicate cache problems?

A: Hit rate (low = ineffective cache or wrong content). Miss latency (slow = stampede or slow source). Eviction rate (high = undersized cache). Memory usage (high = potential for larger cache). Key distribution (few hot keys = good, even = may not need cache). Stale hit rate if trackable.
