HUMAN: We're implementing a distributed transaction log. How do we handle log compaction without losing important data?

A: Log compaction: remove obsolete entries to bound log size. Strategies: key-based (keep latest value per key, Kafka-style), time-based (delete entries older than threshold), or checkpoint-based (entries before checkpoint can be removed). Critical: ensure all consumers can still make progress.

H: How does key-based compaction work?

A: For each key, only latest value matters (if you're replaying state). Compaction: keep latest entry per key, remove older entries. Tombstones: special marker for deletes, retained briefly then removed. Result: log contains snapshot of current state, not full history.

H: What about consumers that are behind during compaction?

A: Consumer at offset 100, compaction removes offsets 50-80. Consumer's offset becomes invalid. Handling: if offset valid, continue; if invalid, options include fail, reset to earliest, or reset to latest. Kafka: offsets reference physical position, not logical sequence.

H: When should we preserve full history vs compact?

A: Preserve for: audit requirements, replay debugging, event sourcing where history matters. Compact for: state replication (latest value sufficient), changelog topics, or when storage is expensive. Often: tiered - full history for N days, compacted beyond. Document retention policy.

H: How do we implement compaction efficiently?

A: Background process: scan log segments, identify keys to compact, write new compacted segment. Considerations: don't compact active segment (still being written), batch compaction (many segments at once), and handle concurrent reads. Monitor: compaction lag, log size, tombstone count.
