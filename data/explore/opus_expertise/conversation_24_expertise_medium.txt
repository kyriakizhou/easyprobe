HUMAN: Our test suite is slow - it takes 20 minutes to run. This slows down our development process significantly.

A: 20 minutes is too long for developer feedback. First, categorize your tests: unit tests should be fast (seconds), integration tests slower, end-to-end slowest. Identify which category is slow. Often the ratio is off - too many slow E2E tests, not enough fast unit tests.

H: Most of our tests hit the database. They set up data, run the feature, check results.

A: Database tests are inherently slower. Strategies: use an in-memory database (SQLite) for tests if possible, run tests in parallel with isolated databases, use database transactions that rollback after each test instead of recreating data. Consider which tests truly need a database.

H: We use PostgreSQL-specific features so SQLite doesn't work. What about test parallelization?

A: Parallelize with database isolation. Options: each parallel worker gets its own database (created from template), or use transaction-based isolation with savepoints. Jest, pytest, and most test runners support parallelization. You'll need to solve test interdependencies first.

H: Some tests depend on global state or specific data setup.

A: That's a test smell. Refactor tests to be independent - each test should set up exactly what it needs. Use factories/fixtures that create minimal required data. Global state creates ordering dependencies and prevents parallelization. It's investment but pays off.

H: What about running only affected tests?

A: Smart test selection helps. Jest can watch mode and run affected tests. For CI, you can use test impact analysis - track which code paths each test covers, only run tests for changed code. Bazel and similar build tools have sophisticated caching.

H: Should we move some tests to run less frequently?

A: Yes! Create test tiers: fast unit tests run on every commit, integration tests on PR creation, full E2E suite nightly or on main branch. Most bugs are caught by fast tests. Save expensive tests for higher-stakes checkpoints.
