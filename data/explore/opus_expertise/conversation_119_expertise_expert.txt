HUMAN: We're implementing a consensus-based metadata store. How do we handle read scalability while maintaining linearizability?

A: Linearizable reads from leader only - doesn't scale. Options: follower reads with confirmation (follower asks leader if up-to-date), lease-based reads (leader grants read lease, follower serves during lease), or read indexes (leader confirms committed, follower waits for index).

H: How does the read index approach work?

A: On read request: ask leader for current commit index. Wait until local log reaches that index. Then serve read locally. Guarantees: read sees all writes committed before request. Overhead: one round-trip to leader per read (can be batched). Used by TiKV, CockroachDB.

H: What about stale reads for less critical operations?

A: Bounded staleness: accept data up to N seconds old. No leader contact needed. Read from any replica with recent heartbeat. Track: how stale is this replica? Document: API exposes staleness choice. Most reads don't need linearizability - huge scalability benefit.

H: How do we implement follower leases?

A: Leader grants time-limited lease to follower. During lease, follower can serve reads without checking leader. Lease requires: synchronized clocks (or conservative clock assumptions). Follower stops serving if lease expires. Leader doesn't grant overlapping leases. Clock drift is the risk.

H: What monitoring is needed for read scalability?

A: Read latency by type (leader, follower, stale). Leader load (is it bottleneck?). Follower freshness (lag to leader). Lease grants and expirations. Read vs write ratio. Cache hit rates if caching metadata. Alert: all reads going to leader (follower read failure).
