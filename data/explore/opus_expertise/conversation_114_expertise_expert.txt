HUMAN: We're implementing a service discovery system. What are the trade-offs between push vs pull models?

A: Pull model: clients periodically fetch service registry. Simple, but stale data between polls, load on registry at scale. Push model: registry notifies clients of changes. More complex, but real-time updates, less polling traffic. Hybrid: long-poll or watch with heartbeat.

H: How does watch-based discovery work?

A: Client opens long-lived connection, receives updates when service list changes. Like etcd watch or ZooKeeper watch. Pros: near-real-time updates, efficient network use. Cons: connection management, handling reconnection, watch gaps during reconnect. Send full state on reconnect, or track revision for incremental.

H: What about health checking in service discovery?

A: Options: self-reporting (service marks itself healthy/unhealthy), active probing (discovery system probes services), or peer monitoring (services probe each other). Self-reporting: simple but service might not know it's unhealthy. Active probing: more accurate but adds load. Usually: combination.

H: How do we handle network partitions in service discovery?

A: Partition: some clients can't reach registry. Options: cache last known state (stale but available), local registry replica (CAP trade-off), or fail closed (no discovery = no calls). Consider: how long to trust cached data? When to start failing? Zone-aware redundancy helps.

H: What's the right consistency model for service discovery?

A: Usually eventual consistency is fine - services tolerate some staleness. But: must not return unhealthy services for too long, must not lose new services for too long. Bounded staleness. For some use cases (leader election): need stronger consistency. Design API to expose consistency guarantees.
