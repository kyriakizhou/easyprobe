HUMAN: What's the difference between horizontal and vertical scaling, and when should I use each?

A: Vertical scaling means adding more power to existing servers - more CPU, RAM, faster disks. Horizontal scaling means adding more servers and distributing load. Vertical is simpler but has limits and single points of failure. Horizontal scales further but adds complexity.

H: We're on a single server now. At what point should I think about horizontal scaling?

A: When your single server consistently runs hot (>70% CPU or memory), when you need zero-downtime deployments, or when you need redundancy for reliability. Many apps run fine on a single beefy server for years. Don't scale horizontally prematurely - it adds real complexity.

H: What complexity does horizontal scaling add?

A: Session management (sessions need to be shared or sticky), file storage (can't use local filesystem), database connections (more servers = more connections), caching consistency, deployment coordination, load balancer configuration, and generally more infrastructure to manage.

H: If I do go horizontal, what changes first?

A: Start by extracting stateful components. Use Redis or a database for sessions instead of memory. Use S3 for file storage instead of local disk. Ensure your app is stateless - any request can go to any server. Then add a load balancer in front of identical app instances.

H: What about the database? That seems like a bottleneck.

A: Database scaling is usually the trickiest. Read replicas help with read-heavy workloads. Connection pooling with PgBouncer helps with connection limits. Caching reduces database load. True horizontal database scaling (sharding) is complex and rarely needed until you're quite large.

H: When does serverless fit in?

A: Serverless (Lambda, Cloud Functions) is extreme horizontal scaling - each request is its own instance. Great for variable traffic, no infrastructure to manage. But cold starts add latency, debugging is harder, and per-request pricing can be expensive at high volume. Consider for specific use cases, not everything.
