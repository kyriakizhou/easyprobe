HUMAN: How do I handle database connection errors gracefully?

A: Connection errors are inevitable - databases restart, networks hiccup. Implement retry logic with exponential backoff, connection health checks, proper error handling, and graceful degradation. Don't crash on transient failures.

H: What errors should I retry versus fail immediately?

A: Retry: connection refused, connection reset, connection timeout (transient issues). Don't retry: authentication failed, database doesn't exist, query syntax errors (won't succeed on retry). Distinguish between infrastructure errors and application errors.

H: How do I implement retry with backoff?

A: Start with short delay (100ms), double each attempt, cap at max delay (30s). Add jitter to prevent thundering herd. Max attempts: 3-5 for API requests, more for background jobs. Libraries like p-retry handle this pattern well.

H: How do I detect connection problems early?

A: Health checks that verify database connectivity. Pool libraries often have health check options. Check before serving traffic. In Kubernetes, fail readiness check if database is unreachable. This routes traffic away while you recover.

H: What about connection pooling during outages?

A: Pool will exhaust during database outage. Configure reasonable wait timeout - don't queue requests forever. Return 503 when pool is exhausted. Monitor pool health. When database recovers, pool will replenish automatically.

H: Should I have a fallback when the database is down?

A: Depends on your app. Read-heavy apps can serve from cache during outages. Some features can degrade (show cached data, queue writes). Critical operations might need to fail. Plan this intentionally - what's acceptable during database outage?
