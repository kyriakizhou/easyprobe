HUMAN: How do I implement proper logging in a production application?

A: Production logging needs structure, levels, and centralization. Use structured logging (JSON), appropriate log levels, correlation IDs for request tracing, and ship logs to a centralized system. Avoid console.log - use a proper logging library.

H: What logging library should I use for Node.js?

A: Pino is fast and produces JSON output. Winston is feature-rich with many transports. Bunyan is also solid. For most cases, Pino is recommended - it's the fastest and works well with modern log aggregation. Whatever you choose, stick with one library consistently.

H: What log levels should I use?

A: Standard levels: error (something broke), warn (concerning but not broken), info (significant events), debug (detailed troubleshooting). In production, usually set to info level. Debug is for development or temporary troubleshooting. Error and warn should be actionable.

H: What information should each log entry contain?

A: Timestamp (ISO format), level, message, and context. Context includes: request_id for tracing, user_id if authenticated, relevant business data. For errors: stack trace, error code. Don't log sensitive data like passwords or tokens.

H: How do I implement request tracing across services?

A: Generate a unique request ID at the entry point. Pass it in headers to downstream services. Include it in every log entry. Use the same field name everywhere (request_id or correlation_id). When debugging, search logs by this ID to see the full request flow.

H: Where should logs go in production?

A: Send to a centralized system: CloudWatch Logs, Elasticsearch/OpenSearch, Datadog, or similar. Don't rely on local files that disappear with containers. Structure logs as JSON for easy querying. Set up alerts on error patterns.
