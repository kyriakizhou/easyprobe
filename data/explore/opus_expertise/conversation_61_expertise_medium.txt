HUMAN: We're deploying to Kubernetes. What are the essential concepts I need to understand?

A: Core concepts: Pods (smallest deployable unit, usually one container), Deployments (manage pod replicas, rolling updates), Services (stable networking for pods), ConfigMaps/Secrets (configuration), Ingress (HTTP routing). Start here, then expand to StatefulSets, Jobs, etc. as needed.

H: What's the relationship between Pods and Deployments?

A: A Deployment manages Pods - it declares "I want 3 replicas of this pod specification." Kubernetes ensures 3 pods are always running. If one dies, Deployment creates a replacement. If you update the Deployment, it handles rolling out new pods gradually.

H: How do I configure my application for Kubernetes?

A: Environment variables and mounted config files. ConfigMaps for non-sensitive config, Secrets for sensitive data. These inject as env vars or files in your containers. Your app should read from environment variables (12-factor app style) - same code works locally and in K8s.

H: How do pods communicate with each other?

A: Services provide stable network endpoints. A Service has a consistent DNS name and IP, routing to pods matching its selector. Pod IPs are ephemeral (change on restart), but Service addresses are stable. Inside cluster: http://service-name.namespace.svc.cluster.local.

H: What about exposing my app to the internet?

A: Ingress controller (nginx-ingress, traefik, or cloud-specific) handles external HTTP traffic. Ingress resources define routing rules: which hostname/path goes to which Service. LoadBalancer Services work too but each gets its own IP, expensive at scale.

H: What's the learning curve like? This seems complex.

A: It is complex initially, but the abstractions are powerful. Start simple: Deployment + Service + Ingress gets your app running. Use Helm charts or operators for complex dependencies (databases). Managed Kubernetes (EKS, GKE) removes cluster management burden. Don't over-engineer early.
