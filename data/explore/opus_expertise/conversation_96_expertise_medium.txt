HUMAN: How do I handle file storage and static assets in my application?

A: Separate concerns: static assets (JS, CSS, images) from user uploads. Static assets: bundle with app or serve from CDN. User uploads: cloud storage (S3, GCS, Azure Blob). Never store user files on app server filesystem in production.

H: Why not store on the app server?

A: Multiple reasons: app servers are ephemeral (can be replaced, scaled), local storage doesn't share across instances, no redundancy or backup, and scaling storage independently from compute is better. Cloud storage is cheap, reliable, and purpose-built.

H: How do I set up S3 for user uploads?

A: Create bucket with proper permissions. Upload flow: user request creates presigned URL, client uploads directly to S3 (saves your bandwidth), S3 returns success, client notifies your server, you store the S3 key in database. For downloads: presigned URLs with expiration.

H: What about image processing - thumbnails, resizing?

A: Options: process on upload (generate all sizes), process on-demand (generate when first requested and cache), or CDN image transformation (Cloudflare, imgix, CloudFront). On-demand is flexible but slower first request. Processed-on-upload is predictable but generates unused sizes.

H: How do I serve files fast globally?

A: CDN in front of storage. CloudFront for S3, Cloudflare, or standalone CDNs. Users fetch from edge location near them. Set appropriate cache headers - static assets can be cached forever (use content hashing in filenames), user content might need shorter TTL.

H: What about cost optimization?

A: Storage tiers: frequently accessed vs cold storage. Move old files to cheaper tiers automatically (S3 lifecycle policies). Compress where appropriate. Delete truly unused files. Monitor costs, set alerts. Presigned URLs have short expiration to prevent hot-linking.
