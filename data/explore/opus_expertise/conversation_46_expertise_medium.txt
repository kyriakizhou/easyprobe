HUMAN: I'm planning data model changes that might break backward compatibility. How do I handle database migrations safely?

A: Breaking changes require careful strategy. The pattern: deploy code that handles both old and new schema, migrate schema, then optionally deploy code that only handles new schema. Never deploy schema changes that break existing running code. What kind of change are you making?

H: Splitting one table into two. Currently "users" has both account and profile data, want separate tables.

A: Good refactoring case. Steps: 1) Create new profile table. 2) Deploy code that writes to both tables and reads from new table with fallback. 3) Backfill historical data to new table. 4) Verify all reads work from new table. 5) Deploy code that only reads/writes new table. 6) Optionally drop old columns.

H: What if the backfill takes a long time?

A: Split into batches, run during low-traffic periods. Track progress in a separate table. Make backfill idempotent so you can resume. Consider running during the "writes to both tables" phase so new data goes directly to new table while you backfill old data.

H: How do I verify data integrity between old and new structure?

A: Dual-read during verification phase: query both sources, compare results, log discrepancies. Run this for hours/days to catch edge cases. Write tests that verify specific known-tricky scenarios. Shadow the new implementation before switching fully.

H: What about foreign keys and constraints?

A: Add constraints after data migration, not before. Otherwise, migration fails on constraint violations. Validate data first: queries that find orphaned records, invalid values, etc. Fix data issues, then add constraints. Consider adding constraints with NOT VALID first, then validating.

H: How do I handle rollback if something goes wrong?

A: Design for rollback from the start. Keep old columns until fully verified (don't drop immediately). Code that writes to both tables means old structure still has current data. If you need to rollback code, old columns are still populated. Only drop after extended success period.
