HUMAN: How do I structure a monorepo for a full-stack application?

A: Monorepos keep related code together: frontend, backend, shared libraries. Structure depends on tooling. Common layout: /apps (deployable applications), /packages (shared code), root config for tooling. Tools like Turborepo, Nx, or pnpm workspaces help manage it.

H: What's the advantage over separate repos?

A: Atomic changes across frontend and backend in one commit. Shared code without publishing to npm. Consistent tooling and configuration. Easier refactoring. Simplified CI that tests everything together. Tradeoff: larger repo, need monorepo tooling.

H: What should go in shared packages?

A: Types/interfaces shared between frontend and backend, validation schemas (zod schemas used both places), API client generated from backend types, utility functions, UI component libraries. Don't share too much - some duplication is fine.

H: How do I set up TypeScript for a monorepo?

A: Root tsconfig.json with shared settings. Each package extends it with its own tsconfig. Use project references for faster builds. Path aliases in each package's tsconfig to reference other packages. Turborepo or Nx handle build ordering automatically.

H: How does CI/CD work with monorepos?

A: Only build/test what changed. Turborepo and Nx have built-in change detection and caching. CI builds affected packages and their dependents. Cache build artifacts between runs. Parallel execution of independent tasks. Significantly faster than building everything.

H: What about deploying different parts to different places?

A: Each app in /apps deploys independently. They share packages at build time but deploy separately. Frontend to CDN, backend to your servers. Docker builds for each app can include only needed packages. Configure CI to deploy only changed apps.
