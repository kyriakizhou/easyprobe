HUMAN: We're building a REST API and need to handle partial updates. PUT vs PATCH?

A: PUT replaces the entire resource with what you send. PATCH partially updates only the fields you send. For user profile updates where users change just their name, PATCH makes more sense - they shouldn't need to resend unchanged fields. PUT is for full replacement.

H: What format should PATCH requests use?

A: Two main approaches. Simple: send JSON with only changed fields, merge with existing. JSON Patch (RFC 6902): send an array of operations like [{"op": "replace", "path": "/email", "value": "new@example.com"}]. Simple is easier; JSON Patch is more precise for complex updates.

H: With simple merge, how do I differentiate between "set to null" and "don't change"?

A: The null ambiguity problem. Options: use a special sentinel value, use JSON Patch operations explicitly, or document that undefined means "don't change" and null means "set to null." Some APIs require DELETE operations for removals instead of null values.

H: How do I handle validation for partial updates?

A: Validate the merged result, not just the patch. The patch itself might be valid, but combined with existing data might create an invalid state. Load current state, apply patch, validate complete object, then persist. Return validation errors referencing the problematic fields.

H: What about concurrent updates? Two users editing the same resource?

A: Optimistic concurrency control. Include an ETag or version number. Client sends If-Match header with their known version. Server rejects if version doesn't match (409 Conflict). Client refreshes and retries. For more complex cases, consider operational transformation or CRDTs.

H: Should PATCH be idempotent?

A: It depends. RFC says PATCH is not required to be idempotent, but your implementation can be. Setting absolute values is idempotent; incrementing values is not. If you need atomic increments, consider a specific endpoint or use JSON Patch operations that are inherently non-idempotent.
