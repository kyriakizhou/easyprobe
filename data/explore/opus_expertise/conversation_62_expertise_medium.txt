HUMAN: I'm writing unit tests but I'm not sure what to test and what level of coverage to aim for.

A: Test behavior, not implementation. Ask: "What should this code do?" Test public interfaces, not private methods. Good test categories: happy path (it works normally), edge cases (empty inputs, nulls, limits), error cases (what happens when things fail?), and critical business logic.

H: What's a reasonable coverage percentage to aim for?

A: Coverage percentage is a tool, not a goal. 100% coverage doesn't mean no bugs. Aim for high coverage on critical paths (payment, authentication, core business logic), less critical for glue code. 70-80% is commonly cited but varies. More important: are you testing the right things?

H: Some of my code is hard to test because it has dependencies on databases and APIs.

A: That's where mocking/stubbing comes in. Replace dependencies with test doubles that return controlled responses. But don't mock everything - integration tests with real dependencies catch problems unit tests miss. Structure code for testability: dependency injection helps.

H: What's the difference between mocks, stubs, and spies?

A: Stub: returns predefined data. Mock: returns data AND verifies how it was called. Spy: wraps real implementation, records calls. Use stubs when you just need controlled returns. Mocks when you need to verify interactions. Spies when you want real behavior but want to observe it.

H: How do I test async code?

A: Most test frameworks handle async well now. In Jest/Mocha, return a promise or use async/await. Test both success and failure paths. Mock timers for testing delays/timeouts without waiting. Be careful with race conditions in tests - flaky tests often come from async issues.

H: Should I test private methods?

A: Generally no - test them through the public interface. If a private method is complex enough to need direct testing, consider if it should be extracted to its own function/class. Testing implementation details makes refactoring harder without adding safety.
