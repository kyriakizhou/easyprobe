HUMAN: We're implementing a distributed workflow orchestration system. How do we handle workflow state persistence and recovery?

A: Workflow state: current step, input/output of each step, timers, and pending activities. Persistence: after each step, before any external action. Recovery: reload state, resume from last persisted point. Journal-based: log state changes, replay on recovery. Or: snapshot + journal.

H: How does event sourcing apply to workflow state?

A: Events: StepStarted, StepCompleted, ActivityScheduled, TimerFired, etc. Workflow state = fold over events. Recovery: replay events. Advantages: full audit trail, deterministic replay. Challenge: must not replay side effects (activities). Use event replay for state, re-trigger pending activities.

H: What about long-running workflows with many steps?

A: Many events = slow recovery. Solutions: periodic snapshots (snapshot state, only replay events after snapshot), or hierarchical (sub-workflows with their own event streams). Also: archive completed workflows, only active workflows in hot storage.

H: How do we handle activity execution guarantees?

A: Activity: external action (API call, computation). At-least-once: schedule activity, if no completion event, retry. Idempotency: activities should handle retries. Heartbeat: long activities report progress, orchestrator knows they're alive. Timeout + retry: dead activity eventually retried.

H: What's the difference between choreography and orchestration?

A: Orchestration: central coordinator directs workflow (Temporal, Cadence). Advantages: visibility, centralized control. Choreography: services react to events independently (saga pattern). Advantages: loose coupling, no single coordinator. Often combined: orchestrator for complex flows, events for simple.
