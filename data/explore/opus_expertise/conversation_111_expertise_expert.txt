HUMAN: We're implementing a distributed ID generator. What are the trade-offs between different approaches?

A: Approaches: UUID (random, no coordination, 128-bit), Snowflake-style (timestamp + machine + sequence, 64-bit, roughly ordered), database sequences (coordinated, potential bottleneck), or segment allocation (allocate ranges, generate locally). Trade-offs: size, ordering, coordination overhead, failure modes.

H: How does Snowflake-style ID generation work?

A: 64 bits: 41 bits timestamp (milliseconds, ~69 years), 10 bits machine ID, 12 bits sequence (4096 per millisecond per machine). Time-ordered: IDs from same millisecond sort by machine then sequence. Needs: synchronized clocks (within tolerance), unique machine IDs, handling clock regression.

H: What happens when clock goes backward?

A: Clock regression: new timestamp < last used timestamp. Options: wait until clock catches up (stalls generation), use last timestamp and exhaust sequence (limited capacity), refuse to generate (fail fast), or logical timestamp that never regresses. Monitor clock sync, alert on drift.

H: How does segment allocation reduce coordination?

A: Central service allocates ranges (1-1000 to server A, 1001-2000 to server B). Servers generate within range without coordination. When range exhausted, fetch new range. Trade-off: segment size vs coordination frequency. Also: wasted IDs if server crashes mid-range.

H: What properties should we consider when choosing?

A: K-sortability: are IDs ordered by creation time? (important for database indexes). Size: 64-bit fits in long, 128-bit needs handling. Uniqueness guarantee: probabilistic (UUID) vs guaranteed (coordinated). Predictability: can attackers guess valid IDs? (security consideration). Distribution: random vs sequential affects index performance.
