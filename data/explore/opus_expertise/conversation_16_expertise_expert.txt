HUMAN: I'm optimizing a hot path in our Go service that processes 50K events/second. Current bottleneck is JSON serialization. What alternatives and optimizations should I consider?

A: JSON serialization is notoriously slow. Alternatives: Protocol Buffers (5-10x faster), FlatBuffers (zero-copy access), MessagePack (binary JSON). For JSON specifically: use jsoniter or easyjson which generate code for specific types. Also consider: is JSON necessary, or can you use a binary format internally?

H: We need JSON for external API compatibility, but internal event processing could use binary.

A: Perfect separation. External APIs: JSON with optimized serializers. Internal event bus: Protocol Buffers or similar. Serialize once at ingress, use binary internally, serialize to JSON only at egress. Reduces serialization from per-operation to per-boundary.

H: We're using encoding/json from standard library. What's the quick win?

A: Switch to jsoniter with ConfigCompatibleWithStandardLibrary for drop-in replacement, 3-5x improvement. For maximum performance, use easyjson or goccy/go-json which generate marshaler/unmarshaler code for your types - avoids reflection entirely.

H: What about the actual struct design? Does field count or types matter?

A: Field count matters less than types. Avoid interface{} fields - they require reflection. Use concrete types. For timestamps, string is slower than int64 epoch. Pointers have overhead - use omitempty with non-pointer types when possible. Keep hot-path structs minimal.

H: We're also doing a lot of map[string]interface{} for dynamic data.

A: Maps are slow to serialize. If the structure is known, define explicit types. For truly dynamic data, consider storing as pre-serialized json.RawMessage - pass through without parsing. Or use a typed wrapper that defers parsing until needed.

H: Any allocation-related optimizations?

A: Huge impact. Use sync.Pool for reusable buffers. Preallocate slice capacity. jsoniter has a pool-backed API. Avoid string concatenation in hot path. Profile with pprof to find allocation hotspots. Memory allocation is often the hidden cost in serialization.
