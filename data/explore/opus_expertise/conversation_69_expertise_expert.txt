HUMAN: We're implementing a distributed scheduler for periodic jobs. What consistency and availability trade-offs are involved?

A: Core challenges: ensuring jobs run exactly once (not missed, not duplicated), handling node failures, and scheduling across time zones. Leader-based: single coordinator decides, simpler but SPOF. Lease-based: nodes claim jobs temporarily. Consensus-based: distributed agreement for each execution.

H: How do we prevent duplicate execution when nodes fail?

A: Fencing: job holder has lease with token. Executor checks token before running, rejects stale. Also: idempotent jobs when possible. At-least-once with dedup (store execution ID, reject reruns). Lock with timeout - if holder dies, lock releases after timeout.

H: How do we handle clock skew in distributed scheduling?

A: Never rely on wall clock for coordination. Use logical time for ordering, wall clock only for human-facing scheduling. For cron-style: each job has next execution time, nodes coordinate on who runs it. Accept that "every minute" might have slight drift across nodes.

H: What's the right data model for job definitions and execution history?

A: Job definition: schedule, handler, config, constraints (which nodes can run). Execution history: job ID, scheduled time, actual start/end, node, status, output/error. Separate tables - definitions are few and updated rarely, executions are many and append-mostly. Partition executions by time.

H: How do we scale the scheduler horizontally?

A: Shard jobs across schedulers by job ID or job group. Each shard uses separate coordination (or single coordinator per shard). Load balance: move jobs between shards based on execution time/resource needs. Monitor: queue depth per shard, execution latency, missed schedules.
