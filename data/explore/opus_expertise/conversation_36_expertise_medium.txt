HUMAN: We're getting complaints about duplicate charges in our payment system. How do I prevent this?

A: Duplicate payments are a serious issue. Main causes: user double-clicking submit buttons, request retries after timeouts, and client bugs. Solutions involve idempotency keys, button state management, and backend deduplication. What payment provider are you using?

H: Stripe. We call their API when users submit payment.

A: Stripe supports idempotency keys - include the same key for retry requests, and Stripe returns the original response instead of creating a duplicate charge. Generate a unique key per payment intent on your frontend, send it with every request for that payment.

H: How do I generate and manage idempotency keys?

A: Generate a UUID when the user lands on payment page, store it in component state or session. Send it as Idempotency-Key header to Stripe. If the user retries or refreshes and tries again, same key = same result. New payment flow = new key.

H: What about the UI side? Users double-click the pay button.

A: Disable the button on first click, show a loading state. Keep it disabled until you get a definitive response. Even with this, don't rely solely on UI - network issues mean retries happen at multiple levels. Server-side idempotency is the real protection.

H: We also have a webhook from Stripe for payment confirmation. Sometimes we get duplicate webhooks.

A: Stripe recommends idempotent webhook handlers. Track which webhook event IDs you've processed in your database. Before processing, check if you've seen this event_id. If yes, return 200 without re-processing. Stripe may retry webhooks, so this is essential.

H: Is there a way to test this without real payments?

A: Stripe's test mode! Use test API keys and test card numbers. Simulate various scenarios: successful payments, failures, duplicate attempts. Write automated tests that verify your idempotency handling. Check your database after tests to confirm no duplicate records.
