HUMAN: We're implementing a distributed file system. How do we handle metadata management at scale?

A: Metadata challenges: single metadata server becomes bottleneck. Solutions: partition metadata by path hash or subtree, replicate for availability, or use distributed KV store. GFS used single master (simplified consistency), HDFS federation partitions namespace, CephFS uses dynamic subtree partitioning.

H: How does subtree partitioning work in CephFS?

A: Directory tree is divided among metadata servers. Hot directories can be migrated or split. Advantages: locality for operations within a subtree. Challenges: cross-subtree operations (rename across partitions), load balancing, and maintaining consistency during migration.

H: What about consistency for file metadata operations?

A: Metadata ops must be atomic and ordered. Options: leader-based replication (Raft/Paxos for each partition), or leases. For inode operations: single authoritative server. For directory operations: may involve multiple inodes. Distributed transactions or careful ordering required.

H: How do we handle client caching of metadata?

A: Clients cache directory listings and file attributes. Invalidation: lease-based (cache valid until lease expires) or callback-based (server invalidates on change). Trade-off: longer leases reduce server load but delay consistency. Also: negative caching for non-existent files.

H: What's the interaction between metadata and data placement?

A: Metadata tracks which storage nodes hold file chunks. Placement policy: spread chunks for availability and parallelism, consider rack/failure domain awareness. Metadata server doesn't handle data - clients talk directly to storage nodes. Reduces metadata server as bottleneck.
