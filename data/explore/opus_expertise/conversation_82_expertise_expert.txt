HUMAN: We're implementing a distributed tracing system's storage backend. What are the key design considerations for trace data?

A: Trace data characteristics: write-heavy, immutable, time-ordered, queried by trace ID or service+time range. Storage: columnar for analytics (service, duration distributions), indexed for trace lookup. Retention: tiered (recent in hot storage, older downsampled or archived).

H: How do we index traces for efficient querying?

A: Primary index: trace ID → spans. Secondary indices: service name, operation name, duration (for slow traces), status (errors), tags (custom attributes). Trade-off: more indices = faster queries, slower writes. Consider: bloom filters for trace ID existence check.

H: What's the right data model for span storage?

A: Span: trace ID, span ID, parent ID, service, operation, start time, duration, status, tags, logs. Denormalize for query efficiency: include trace-level info in each span. Or: separate trace metadata table. Consider: span links for cross-trace relationships (batch job spawning).

H: How do we handle high-cardinality tag values?

A: Tags like user ID create index explosion. Solutions: selective indexing (only index known tags), tag value truncation/hashing for index, or separate high-cardinality lookup (query by trace ID first, then filter). Document which tags are indexed vs filterable.

H: What sampling decisions should the storage support?

A: Store sampling decision with trace: was it head-sampled, tail-sampled, or force-sampled? Enables: accurate rate extrapolation, different retention by sample type. Also store: original sampling rate for statistical correction. Query interface should indicate sampled vs complete data.
