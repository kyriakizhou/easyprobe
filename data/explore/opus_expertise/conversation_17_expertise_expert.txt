HUMAN: We're implementing a saga pattern for distributed transactions across our microservices. How do we handle compensating transactions that fail?

A: Compensating transaction failure is the hardest part of sagas. Options: retry compensation indefinitely (eventual completion), dead letter queue for manual intervention, or design compensations to be always-successful through idempotent operations that accept current state gracefully.

H: Can you elaborate on designing compensations that always succeed?

A: Instead of "undo X", design as "ensure X didn't happen". CancelOrder doesn't fail if order already cancelled - it confirms cancellation. ReleaseInventory doesn't fail if inventory never reserved - it confirms availability. Compensations become state assertions rather than mutations.

H: What if the compensation depends on an external service that's down?

A: This is where saga orchestration complexity lives. Options: circuit breaker with queued retry (eventually consistent compensation), synchronous retry with exponential backoff, or alert for human intervention. Document SLA for compensation completion.

H: How do we track saga state across failures and retries?

A: Saga orchestrator persists state machine. States: Started, Step1Complete, Step2Complete, Compensating, Compensated, Failed. On restart, orchestrator resumes from persisted state. Each step transition is durable. Use distributed workflow engines (Temporal, Cadence) rather than building custom.

H: We built a custom saga orchestrator. It's becoming hard to maintain. Worth migrating to Temporal?

A: Probably yes. Temporal handles: durable state, automatic retries, visibility, versioning, and exactly-once semantics. The learning curve is real but it's solving genuinely hard problems. Custom saga orchestrators tend to accumulate edge cases that frameworks have already solved.

H: What about performance? Temporal adds network hops.

A: Temporal is designed for correctness in distributed transactions - some latency is acceptable. For high-throughput sagas, consider: batch operations where possible, parallel saga steps, and evaluate whether you really need saga semantics or if eventual consistency with simpler patterns suffices.
