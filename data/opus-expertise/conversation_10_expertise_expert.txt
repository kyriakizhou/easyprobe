HUMAN: I'm seeing occasional deadlocks in our PostgreSQL database during high concurrency. How do I diagnose and prevent them?

A: Deadlocks occur when transactions wait for locks held by each other in a cycle. PostgreSQL automatically detects and aborts one transaction, but they indicate design issues. Check pg_stat_activity and pg_locks during the deadlock, or enable log_lock_waits and deadlock_timeout for automatic logging.

H: I enabled logging and see two UPDATE statements deadlocking on the same table but different rows. How is that possible?

A: Row-level locks shouldn't deadlock unless there's an ordering issue. Check if your queries use index scans - gap locking isn't an issue in PostgreSQL, but if you're updating rows found via different index paths in different orders, you could hit this. Also verify you're not escalating to table locks.

H: The queries are UPDATE accounts SET balance = balance - $1 WHERE id = $2. Two transactions are transferring between the same accounts in opposite directions.

A: Classic case. Transaction 1 locks account A, then tries to lock B. Transaction 2 locks account B, then tries to lock A. Solution: always acquire locks in a consistent order. Sort account IDs and always lock the lower ID first, regardless of transfer direction.

H: How do I implement that ordering without making two separate queries?

A: Use SELECT ... FOR UPDATE with the sorted IDs first, then do the updates. Or use a single UPDATE with a CTE that ensures ordering: WITH sorted AS (SELECT id FROM accounts WHERE id IN ($1, $2) ORDER BY id FOR UPDATE) UPDATE accounts... This guarantees consistent lock acquisition order.

H: What about more complex scenarios where the lock order isn't obvious?

A: For complex transactions, consider: advisory locks to serialize access at application level, shorter transactions (reduce lock hold time), optimistic concurrency with version columns and retry logic, or redesigning to avoid concurrent updates to related rows.

H: How do I monitor for deadlock frequency in production?

A: Track deadlock_timeout occurrences in logs. Query pg_stat_database for deadlocks column. Alert if deadlock rate exceeds threshold. Include deadlocked query text in alerts. Periodic review of patterns helps identify systemic issues versus one-off occurrences.
