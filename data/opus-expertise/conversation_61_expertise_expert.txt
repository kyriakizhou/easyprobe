HUMAN: We're building a real-time stream processing system. How do we handle late-arriving data and out-of-order events?

A: Core concept: event time vs processing time. Watermarks indicate "all events before time T have arrived." Late data: extend watermark tolerance, use allowed lateness window, or side output for late events. Windowing: tumbling, sliding, session - all need watermark handling.

H: How do we generate accurate watermarks?

A: Heuristic watermarks: max event time seen minus some slack. Punctuation watermarks: special events in the stream. Source-aware: Kafka partition timestamps. Multi-source: take minimum across all sources. Trade-off: tighter watermarks = more late data, looser = more latency.

H: What happens when events are significantly out of order?

A: Define "allowed lateness" - window results update if late event arrives within this period. Beyond that: drop or side-output. Implementation requires maintaining window state beyond the watermark. State can grow large for wide allowed lateness windows.

H: How do we maintain exactly-once semantics with failures?

A: Checkpointing: periodically snapshot operator state and input positions. On failure, restore from checkpoint, replay from that position. Requires: deterministic processing, idempotent sinks, or transactional sinks. Flink, Kafka Streams provide exactly-once guarantees this way.

H: What about backpressure handling?

A: Backpressure: slow consumer signals to producer. Implementation: credit-based flow control, or bounded queues with blocking. Propagates upstream to sources. Important: don't drop data, slow the whole pipeline. Monitor: queue depths, processing latency to detect backpressure.
