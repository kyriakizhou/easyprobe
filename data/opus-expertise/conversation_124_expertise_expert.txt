HUMAN: We're implementing a multi-tenant database architecture. How do we ensure tenant isolation while sharing infrastructure?

A: Isolation models: separate databases (strongest, expensive), separate schemas (good isolation, some sharing), shared tables with tenant ID (most efficient, weakest isolation). Choice depends on: security requirements, tenant size variance, operational complexity tolerance.

H: How do we prevent query leakage in shared-table model?

A: Row-level security: database enforces tenant filter on all queries. Application-level: always include tenant_id in WHERE, audit for violations. ORM middleware: inject tenant filter automatically. Testing: verify queries can't access other tenants. Defense in depth: multiple layers.

H: What about noisy neighbor problems?

A: One tenant's heavy query affects others. Solutions: per-tenant resource quotas (connection limits, query timeout), query cost estimation and rejection, or priority queuing. Also: separate read replicas for heavy analytics. Monitor: per-tenant resource consumption.

H: How do we handle tenant-specific schema requirements?

A: Options: JSON column for tenant-specific data (flexible but hard to index), entity-attribute-value (normalized but complex queries), or extension tables (tenant-specific tables). Consider: how common are customizations? Can you push to application layer instead?

H: What's the migration path between isolation models?

A: Growing tenant might need more isolation. Shared → dedicated: extract tenant data to new database, redirect traffic, handle transition window. Automation critical for sustainability. Design for this from start: abstract tenant location, support multiple backends.
