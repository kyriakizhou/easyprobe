HUMAN: We're seeing lock contention in our PostgreSQL database at high concurrency. EXPLAIN shows RowExclusiveLock waits. How do we diagnose and address this?

A: RowExclusiveLock on heap is normal for writes but shouldn't cause excessive waiting unless there's contention on same rows, lock escalation, or long-running transactions holding locks. Check pg_locks and pg_stat_activity together to see what's waiting on what.

H: I see many transactions waiting on the same tuple. They're UPDATE statements on the same counter row.

A: Classic hot-spot pattern. Single row updated by many transactions serializes access. Solutions: advisory locks to serialize application-side, optimistic locking with retry, sharding the counter across multiple rows, or moving counter updates to async aggregation.

H: How would sharding a counter work?

A: Instead of one row with count, have N rows each with partial_count. Increment a random shard: UPDATE counters SET value = value + 1 WHERE shard_id = random_shard(). Total count is SUM(value). Reduces contention by N. Trade-off: reads become more expensive.

H: We also see contention on index updates. GIN index on a frequently updated column.

A: GIN indexes lock during updates because of their internal structure. Solutions: reduce GIN index update frequency (fastupdate setting), use B-tree if query patterns allow, or accept the contention. Alternatively, separate hot update paths from indexed columns.

H: What about foreign key checks causing lock waits?

A: FK checks take ShareLock on referenced table. High-volume inserts to child table can contend with updates to parent table. Consider: deferring FK checks to commit (SET CONSTRAINTS DEFERRED), denormalizing if FK isn't needed, or batching child inserts.

H: How do I monitor for lock contention proactively?

A: pg_stat_activity shows wait_event_type = 'Lock'. log_lock_waits = on logs waits exceeding deadlock_timeout. Track lock wait time in monitoring. pg_locks shows current locks. Alert on sustained high lock waits. Periodic snapshot of pg_locks for analysis.
