HUMAN: What database indexing strategies should I know for a web application?

A: Essential indexes: primary key (automatic), foreign keys for joins, columns used in WHERE clauses, columns used in ORDER BY. Composite indexes for multi-column conditions. Covering indexes that include all selected columns avoid table lookups. Start with query patterns, add indexes as needed.

H: How do I know if my query is using indexes?

A: Use EXPLAIN (PostgreSQL) or EXPLAIN ANALYZE. Look for Index Scan (good) vs Seq Scan (often bad on large tables). Check "rows" estimates vs actual. EXPLAIN ANALYZE shows actual execution time. Run it on slow queries to understand what's happening.

H: When would I use a composite index vs multiple single-column indexes?

A: Composite index: (user_id, created_at) for queries filtering/sorting by both. Follows leftmost prefix - works for user_id alone, user_id + created_at, but not created_at alone. Multiple separate indexes: database can combine them but less efficiently. Composite is better for specific query patterns.

H: What about indexing for LIKE queries?

A: LIKE with leading wildcard ('%term') can't use B-tree indexes - requires full scan. LIKE without leading wildcard ('term%') can use indexes. For full-text search, use specialized indexes: PostgreSQL's GIN with tsvector, or dedicated search engines like Elasticsearch.

H: Should I index everything?

A: No! Indexes have costs: storage space, slower writes (insert/update/delete must update indexes), and optimizer overhead. Index selectively based on actual query patterns. Monitor unused indexes and remove them. A heavily-indexed table can have slower writes than reads.

H: How do I handle slowly growing tables? Index that's fine now might not scale.

A: Monitor query performance over time. Set up slow query logging. Re-analyze with EXPLAIN as data grows. Sometimes you need to restructure indexes, add partitioning, or archive old data. What works at 10K rows might not work at 10M.
