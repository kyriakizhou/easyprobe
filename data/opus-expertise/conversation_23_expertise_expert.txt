HUMAN: We're implementing a global CDN caching strategy. How do we handle cache invalidation across edge locations when content changes?

A: CDN cache invalidation is inherently eventually consistent. Options: purge API (slow, expensive at scale), surrogate keys for grouped invalidation, short TTLs with stale-while-revalidate, or versioned URLs (cache forever, new version is new URL).

H: We use Cloudflare. Purge takes 30+ seconds globally. For real-time content updates, that's too slow.

A: For real-time: don't cache, or use very short TTL with stale-while-revalidate. User gets stale content instantly while edge fetches fresh. Alternatively, versioned URLs: change URL on content update, new URL is cache miss, immediately fetches fresh.

H: Versioned URLs work for assets, but our API responses are at fixed endpoints.

A: For APIs: Cache-Control: max-age=1, stale-while-revalidate=59. Content is fresh for 1 second, then stale but served while revalidating for 59 more seconds. Users rarely wait more than 1 second for fresh data. Tune based on your freshness requirements.

H: What about using cache tags for selective invalidation?

A: Cloudflare (Enterprise) and Fastly support surrogate keys/cache tags. Tag responses: Cache-Tag: product-123, category-456. On product update, purge by tag. All edge locations with that tag purge. Still takes time, but more targeted than URL-based purge.

H: How do we handle personalized content that shouldn't be cached?

A: Mark as private: Cache-Control: private, no-store. Or use edge computing (Workers, Lambda@Edge) to separate cacheable base from personalized overlay. Cache the template, inject personalization at edge. Also: vary header properly - Vary: Authorization caches per-user (careful with cardinality).

H: What monitoring should we have for cache performance?

A: Track hit rate per endpoint/pattern. Alert on hit rate drops - might indicate caching bug or traffic pattern change. Monitor origin load - high origin requests might mean ineffective caching. Check cache-status headers in responses to understand caching behavior.
