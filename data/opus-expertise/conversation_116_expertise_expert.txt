HUMAN: We're implementing a distributed rate limiter. How do we handle the latency vs accuracy trade-off?

A: Central rate limiter: accurate but adds latency to every request. Distributed: local rate limiting with periodic sync. Accept over-limit within sync window. Trade-off: tighter sync = more accurate, higher overhead. For most cases: local limiting with async background sync is good enough.

H: How does the token bucket algorithm work in distributed settings?

A: Each node has local bucket with portion of global rate. Tokens replenish from central allocation or proportional to time. Sync: report consumption, get allocation adjustment. Skew handling: nodes consuming more get larger share. Overflow: tokens that would exceed bucket are wasted (or redistributed).

H: What about sliding window rate limiting?

A: Sliding window: count requests in last N seconds. More accurate than fixed windows (no boundary bursts). Distributed: each node counts locally, sync counts periodically. Approximation: weighted sum of current and previous window. Redis sorted sets can implement exactly with timestamp scores.

H: How do we handle rate limit quotas across multiple dimensions?

A: Dimensions: per-user, per-API, per-IP, global. Apply all limits, reject if any exceeded. Implementation: separate counters per dimension, check all on request. Efficiency: can batch checks for same request. Consider: hierarchical limits (user limit within global limit).

H: What's the best response when rate limited?

A: HTTP 429 with Retry-After header. Include: which limit was exceeded (helps debugging), reset time, remaining quota. For APIs: rate limit headers on all responses (X-RateLimit-*). Client guidance: exponential backoff, respect Retry-After, implement client-side throttling.
