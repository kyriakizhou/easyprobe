HUMAN: I need to implement rate limiting in my API. What approaches work well for production?

A: Several options depending on your scale. Simplest is token bucket or sliding window algorithms implemented with Redis. For distributed systems, you need shared state - Redis is the common choice. Higher scale might use a dedicated rate limiting service or API gateway features.

H: We're using Node.js with multiple instances behind a load balancer. Currently no Redis.

A: You'll need shared state for consistent rate limiting across instances. Redis is the most common solution - lightweight, fast, and has atomic operations perfect for counters. Libraries like rate-limiter-flexible make implementation straightforward.

H: What's the difference between token bucket and sliding window?

A: Token bucket: tokens refill at a fixed rate, requests consume tokens. Allows bursts up to bucket size. Sliding window: counts requests in a moving time window, smoother rate enforcement. Fixed window is simpler but has the "thundering herd" problem at window boundaries.

H: Should I rate limit by IP address or user?

A: Both! IP-based catches unauthenticated abuse and protects login endpoints. User-based limits authenticated users fairly. Different endpoints might need different limits - public search might be stricter than user's own data. Consider tiered limits based on subscription level too.

H: How do I communicate limits to API clients?

A: Return standard headers: X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset. When limited, return 429 Too Many Requests with a Retry-After header. This helps well-behaved clients back off appropriately and retry at the right time.

H: What about protecting against DDoS specifically?

A: Application-level rate limiting helps but isn't sufficient for real DDoS attacks. Use a CDN with DDoS protection (Cloudflare, AWS Shield) as your first line of defense. They can absorb volumetric attacks that would overwhelm your servers before requests even reach you.
