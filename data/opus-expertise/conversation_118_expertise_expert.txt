HUMAN: We're implementing an event sourcing system. How do we handle the read model rebuild when projection logic changes?

A: Projection change: old events need reprocessing with new logic. Rebuild: replay all events through new projection, build new read model. Strategies: blue-green (build new model, switch when ready), or incremental (process events, serve partial results). Consider rebuild time and resource impact.

H: How do we handle very long event streams efficiently?

A: Snapshots: periodically save projection state, rebuild from snapshot + newer events only. Snapshot frequency: balance storage vs rebuild time. Also: event archiving (old events to cold storage, load on demand), and parallel replay (partition events, rebuild partitions concurrently).

H: What about schema evolution of events themselves?

A: Events are immutable but need interpretation. Options: upcast on read (transform old format to new at deserialization), versioned event handlers (different logic per version), or event migration (controversial - modifies history). Upcast most common, keeps handlers clean.

H: How do we handle projections that need data from multiple aggregates?

A: Cross-aggregate projections: need events from multiple streams. Options: project into same read model from multiple handlers, event correlation (join events by correlation ID), or saga-style coordination. Challenge: ordering across streams (timestamps help, logical order better).

H: What testing strategy works for event sourcing?

A: Given-when-then: given these events, when this command, then these events emitted. Test projections: given these events, projection state should be X. Test rebuilds: projection from scratch equals projection incrementally built. Property testing: random event sequences should produce valid state.
