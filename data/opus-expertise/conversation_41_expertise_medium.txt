HUMAN: Our API responses are getting inconsistent. Some endpoints return arrays, some return objects with data property. Any recommendations?

A: API response consistency improves developer experience significantly. A common pattern: always return an object with consistent structure. For single items: {"data": {...}}. For lists: {"data": [...], "meta": {...}}. For errors: {"error": {...}}. Never mix or return raw arrays.

H: What should go in the meta object?

A: For paginated lists: page info (cursor, total count, has_more). For any response: request_id for support/debugging. Some APIs include rate limit info. Timestamps can help with caching. Keep it minimal but include what clients need to make decisions.

H: Should we use HTTP status codes or error codes in the body?

A: Both! Use appropriate HTTP status codes (4xx for client errors, 5xx for server errors) AND include error details in the body. Status codes enable standard HTTP handling; body provides actionable info: {"error": {"code": "INVALID_EMAIL", "message": "Email format is invalid", "field": "email"}}.

H: How do we handle partial failures? Like a bulk operation where some items succeed?

A: Return 200 (the request succeeded) with a response showing individual results. {"data": [{"id": 1, "status": "success"}, {"id": 2, "status": "failed", "error": {...}}]}. Or 207 Multi-Status if you want to be HTTP-purist. Don't use 500 for partial failures.

H: What about empty states? Empty list vs null?

A: Return empty array for lists with no items: {"data": []}. Never null for lists. For optional singular fields, null is acceptable but document it. Be consistent. Some prefer not returning the field at all vs returning null - either works if documented.

H: How should we document this consistently?

A: OpenAPI/Swagger is the standard. Define base response schemas that specific endpoints extend. Include examples. Auto-generate docs from code if possible (many frameworks support this). Document error codes and what triggers them. Keep docs near code so they stay current.
