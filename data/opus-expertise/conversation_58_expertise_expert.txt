HUMAN: We're implementing a lock-free data structure for high-throughput logging. What are the key challenges with lock-free ring buffers?

A: Lock-free ring buffers: producers claim slots via atomic increment of write index, consumers read from read index. Challenges: handling wrap-around, preventing producers from overwriting unread data, and ensuring memory visibility. LMAX Disruptor is the canonical high-performance example.

H: How does the Disruptor handle multiple producers?

A: Two-phase approach: producers first claim a slot (CAS on sequence), then write data, then publish (make visible to consumers). The "cursor" tracks the lowest unpublished slot. Consumers wait for the cursor to advance past their position. This handles the "slow producer" problem.

H: What about false sharing in the ring buffer?

A: False sharing kills performance. Pad sequence counters and frequently-accessed fields to cache line boundaries (usually 64 bytes). Also consider: producer and consumer on different cores, NUMA effects. Benchmark with perf c2c or similar tools to detect false sharing.

H: How do we handle slow consumers that fall behind?

A: Options: drop events (acceptable for metrics/logging), block producers (back-pressure), or expand buffer dynamically. For logging: ring buffer with overflow to disk, consumer catches up from disk when behind. Alert on consumer lag to prevent data loss.

H: What's the memory ordering required for correctness?

A: Acquire-release semantics at minimum. Producer: release fence after writing data, before publishing. Consumer: acquire fence after reading sequence, before reading data. Some architectures (x86) provide stronger guarantees, but code for the weakest model for portability.
