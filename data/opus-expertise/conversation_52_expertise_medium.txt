HUMAN: Our PostgreSQL queries are slow on some pages. How do I identify and fix slow queries?

A: Start with query identification. Enable pg_stat_statements extension to track query performance. Also check slow query log (log_min_duration_statement). Look for queries with high total time, high call count, or high average time. Which will you check first?

H: I enabled pg_stat_statements. I see a query taking 500ms average called 1000 times per hour.

A: That's a big impact - 500 seconds total per hour. Run EXPLAIN ANALYZE on that query to understand the execution plan. Look for: sequential scans on large tables (missing index), nested loops with many iterations, and sort operations on large result sets.

H: The explain shows "Seq Scan on orders" with 500,000 rows. We're filtering by user_id and order_date.

A: Missing composite index. Create: CREATE INDEX idx_orders_user_date ON orders(user_id, order_date). Order matters - put equality conditions first, range conditions last. After creating, run EXPLAIN ANALYZE again to verify it uses the index.

H: The index helped that query, but now another is slow. It has multiple JOIN and subqueries.

A: Complex queries need careful analysis. Check join order in the explain plan - sometimes PostgreSQL chooses suboptimal order. Ensure foreign keys have indexes. Consider if you need all that data or can denormalize. Sometimes restructuring the query or breaking into multiple queries helps.

H: How do I prevent slow queries from impacting the whole system?

A: Statement timeout prevents runaway queries: SET statement_timeout = '30s'. Connection pooling (PgBouncer) prevents connection exhaustion. Read replicas offload read-heavy queries. Query-level timeout in application code as backup. Monitor query times and alert on degradation.

H: Should I optimize everything or is some slowness acceptable?

A: Optimize what impacts users - pages they access frequently, APIs with strict SLAs. A nightly report that takes 10 seconds is different from a checkout API taking 10 seconds. Set performance budgets (p95 < 200ms for user-facing APIs) and prioritize violations.
