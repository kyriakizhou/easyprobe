HUMAN: We're implementing a distributed snapshot isolation system. What are the implementation challenges?

A: Snapshot isolation: transactions see consistent snapshot, concurrent writes to same key conflict. Challenges: assigning globally consistent snapshot timestamps, detecting write-write conflicts efficiently, and garbage collecting old versions. Distributed adds: clock synchronization, cross-shard transactions.

H: How do we assign consistent snapshot timestamps across shards?

A: Options: centralized timestamp oracle (single point of failure but consistent), Lamport clocks (logical time, happens-before ordering), or hybrid logical clocks (bounded by real time, logical ordering). Google Spanner: TrueTime with bounded clock uncertainty.

H: What's the write-write conflict detection mechanism?

A: Track: for each key, list of transactions that wrote it. On commit: check if any concurrent transaction wrote same key. Conflict = abort one transaction. Optimization: track at key-range or lock level, not individual keys. First-committer-wins or first-updater-wins policies.

H: How does TrueTime enable strong consistency?

A: TrueTime: returns time interval [earliest, latest] containing actual time. To commit: wait until you're sure your commit timestamp has passed everywhere. Wait = 2× clock uncertainty (typically ~7ms). After wait: guaranteed that all readers with later timestamp will see write.

H: What about read-only transactions for lower latency?

A: Read-only: no conflict detection needed. Assign snapshot timestamp at transaction start. All reads see data as of that timestamp. Challenge: some shards might not have data that recent yet (lag). Solution: wait for shard to catch up, or use older timestamp.
