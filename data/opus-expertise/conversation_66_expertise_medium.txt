HUMAN: I need to implement a simple queue in my application. Should I use Redis, RabbitMQ, or just a database table?

A: For simple needs, a database table queue works fine and reduces infrastructure. Redis (with Bull) adds reliability and better performance. RabbitMQ adds sophisticated routing and guarantees. What's your scale and reliability requirement?

H: Maybe a few hundred jobs per hour. Sending emails, generating reports.

A: At that scale, a database table queue might be sufficient - simple to implement, no new infrastructure. Table with columns: id, type, payload, status, created_at, processed_at. Workers poll for pending jobs. Add index on status and created_at for efficient queries.

H: What are the downsides of database-backed queues?

A: Polling has latency and database load. Row locking for job claims can bottleneck. No built-in delayed jobs, retries, or priority without custom code. Missing features you'd get free from dedicated queue systems. But for simple needs, it works.

H: When should I upgrade to Redis or RabbitMQ?

A: Signs you've outgrown database queues: job processing latency matters (polling is too slow), high job volume causing database contention, need for priority queues or delayed jobs, or reliability requirements where job loss is unacceptable. Redis with Bull covers 90% of cases.

H: How does job failure handling work?

A: Mark job as failed after max retries. Store error message for debugging. Options: leave in failed status for manual review, retry with exponential backoff, or move to dead letter queue. Bull has all this built-in. For database queues, implement retry logic yourself.

H: What about job deduplication? We don't want the same email sent twice.

A: Use unique constraints on job payload hash or business identifier. Before enqueueing, check if pending/processing job with same identifier exists. Idempotency keys work well - include in payload, check before processing. At-least-once delivery is common; design handlers to be idempotent.
