HUMAN: We're implementing a distributed permission system. How do we handle permission checks at scale without adding latency to every request?

A: Permission check latency is critical - on every request. Options: cache permissions aggressively (with invalidation on change), push permissions to edge (services have local permission data), or precompute access control lists. Trade-off: consistency vs latency.

H: How do we implement permission caching safely?

A: Cache by (subject, resource, action). TTL-based expiration for staleness bound. Invalidation: when permissions change, publish invalidation events. Challenge: invalidation fan-out (one role change affects many cached entries). Consider: negative caching (cache "denied" results too).

H: What about hierarchical permissions with inheritance?

A: Folder permissions inherited by files. Caching challenge: change at folder affects all descendants. Options: flatten hierarchy at write time (denormalize), or expand hierarchy at read time (more complex queries). Google Zanzibar: expand on read with aggressive caching.

H: How does Google Zanzibar handle scale?

A: Relation tuples: (object, relation, subject). Check: is this tuple present, or transitively derivable? Index by object and by subject for efficient queries. Caching at multiple levels. Consistency: zookies (consistency tokens) ensure check reflects recent writes. Highly optimized for read-heavy.

H: What consistency guarantees are appropriate for permissions?

A: Too stale: removed user still has access (security issue). Too strict: latency unacceptable. Typical: read-your-writes for permission changes (user removes access, sees it immediately). Bounded staleness for others. Zookies: client passes token, server ensures check is at least as fresh.
