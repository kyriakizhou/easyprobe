HUMAN: We're implementing a distributed tracing system. How do we handle trace context propagation across async boundaries and different protocols?

A: Trace context must survive: HTTP headers (W3C Trace Context standard), message queue messages (custom headers), gRPC metadata, and async execution (thread/coroutine handoffs). Each boundary is a potential break point. Use instrumentation libraries that handle common cases; custom code for exotic boundaries.

H: We use Kafka extensively. Messages might be processed days after production. Should we continue the trace?

A: Philosophical question. Processing the same message is technically the same "transaction" but the time span makes single-trace visualization useless. Common approach: link traces - new trace for processing links to original producer trace. Preserves causality without absurd durations.

H: How do we handle fan-out? One request triggers 100 async workers.

A: Each worker gets child span under the parent. But 100 children clutter the trace. Options: sample aggressively (trace 1% of workers), use span links instead of parent-child (related but separate traces), or aggregate worker spans into a single "processing" span with count metadata.

H: What about context propagation in Go with goroutines?

A: Go context.Context carries trace context. When spawning goroutines, pass context explicitly. For goroutine pools, inject context per-task. Instrumented libraries (opentelemetry-go) handle http.Handler context automatically. Watch for lost context in background goroutines.

H: We're seeing high cardinality in our tracing backend from user-specific tags. How do we manage this?

A: High cardinality (user_id, request_id as indexed tags) explodes storage and query costs. Strategies: move high-cardinality to span logs/events (not tags), use exemplars (sample specific traces, link from metrics), or purpose-built backends like Tempo that handle high cardinality better.

H: How do we correlate traces with logs and metrics?

A: Include trace_id and span_id in all logs. Structured logging makes this queryable. For metrics, exemplars link metric samples to traces. Grafana's unified observability approach: jump from metric spike → exemplar trace → relevant logs. OpenTelemetry standardizes this across signals.
