HUMAN: I'm implementing password reset functionality. What's the secure way to do this?

A: The standard secure flow: user requests reset with email, generate a cryptographically random token with expiration, store the hash (not the token itself), email the token in a link, user clicks link and provides new password, verify token hash and expiration, update password and invalidate token.

H: Why hash the token if it's already random?

A: Defense in depth. If an attacker gets database access (through SQL injection or backup leak), plain tokens let them reset any account. Hashed tokens are useless without the original. Use bcrypt or similar with the same precautions as passwords.

H: How long should the token be valid?

A: Short enough to limit exposure, long enough to be usable - typically 1-24 hours. Consider your users: B2B SaaS might use shorter (users check email promptly), consumer apps might need longer. Show expiration time in the email so users know.

H: What if someone requests multiple reset tokens?

A: Options: invalidate previous tokens when a new one is generated, or allow multiple valid tokens. Single valid token prevents replay but might frustrate users who request twice. I prefer invalidating old ones - simpler security model and encourages users to use the latest email.

H: How do I prevent attackers from using reset to enumerate valid emails?

A: Never indicate whether the email exists. Return the same message ("If an account exists, we've sent a reset email") regardless of whether the email is in your database. This prevents attackers from discovering valid user emails through the reset form.

H: Should I require re-authentication for changing other sensitive settings?

A: Yes! Sensitive operations (change email, change password, enable 2FA, delete account) should require current password even for logged-in users. This protects against session hijacking and CSRF. Some apps also require re-auth after a period of inactivity.
