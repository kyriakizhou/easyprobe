HUMAN: We're implementing a distributed snapshot system for consistent backups. How does the Chandy-Lamport algorithm work?

A: Chandy-Lamport: marker-based snapshot without stopping the system. Initiator records local state, sends marker on all outgoing channels. On receiving first marker: record local state, send markers out. For each channel: record messages between own snapshot and marker arrival. Gives consistent global state.

H: What assumptions does Chandy-Lamport require?

A: Requirements: FIFO channels (messages arrive in order sent), reliable delivery (no message loss), strongly connected graph (markers reach all processes). Non-FIFO channels need sequence numbers. Unreliable channels need acknowledgments and retransmission. Real systems often adapt the algorithm.

H: How do we apply this to database snapshots?

A: Database adaptation: snapshot transaction starts, gets timestamp T. All reads see state as of T. Concurrent writes with timestamp > T are invisible to snapshot. MVCC naturally supports this. For distributed database: coordinate snapshot timestamp across nodes, ensure all see consistent time.

H: What about incremental snapshots?

A: Full snapshot expensive. Incremental: track changes since last snapshot, only backup changed data. Implementation: change tracking with LSN/timestamps, or copy-on-write at block level. Restore: apply increments on top of full backup. Trade-off: restore time increases with more increments.

H: How do we verify snapshot consistency?

A: Checksums at multiple levels: block, file, and logical. After restore: run consistency checks (database fsck equivalent). Compare counts and checksums between source and restored. Test restores regularly - backup that can't restore is useless. Automate verification in backup pipeline.
