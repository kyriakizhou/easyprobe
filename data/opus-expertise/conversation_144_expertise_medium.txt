HUMAN: How do I implement proper API request throttling and queuing?

A: Throttling limits request rate to external APIs that have rate limits. Queue requests when over limit, process at allowed rate. Handle retries for 429 responses. Different from rate limiting (protecting your own API).

H: What's the difference between throttling and rate limiting?

A: Rate limiting: you protecting your API from too many requests. Throttling: you limiting your requests to external APIs that have rate limits. You're on the receiving end of throttling, generating end of rate limiting.

H: How do I implement client-side throttling?

A: Use a rate limiter/throttler library. Queue outgoing requests. Release at allowed rate (e.g., 10 requests per second). Different external APIs have different limits - configure per API. Handle burst allowances if the API supports them.

H: How do I handle 429 Too Many Requests responses?

A: Read Retry-After header if present. Back off and retry. Don't retry immediately - respect the indicated wait time. After retry, if still failing, increase backoff. Log rate limit hits for monitoring.

H: What about shared rate limits across multiple instances?

A: If your rate limit is 100/minute globally across all your servers, coordinate. Use Redis to track shared request count. Before each request, check and increment counter. Wait if over limit. Distributed rate limiting is tricky.

H: How do I prioritize requests when throttled?

A: Queue with priorities. Critical requests (payment, auth) go first. Background sync can wait. Separate queues per priority. Process high priority queue first. Consider timeout - old requests may not be worth sending.
