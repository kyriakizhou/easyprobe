HUMAN: We're building a CDC (Change Data Capture) pipeline. What are the architectural patterns for consuming database changes reliably?

A: CDC approaches: log-based (parse WAL/binlog - Debezium), trigger-based (database triggers write to outbox), or polling-based (timestamp columns). Log-based is least invasive and most reliable. Key concern: exactly-once semantics downstream - usually achieved via idempotency or transactional outbox.

H: How does Debezium handle schema changes?

A: Debezium tracks schema history, stores DDL in a separate topic. When schema changes, new events use new schema. Consumers must handle schema evolution - Avro with schema registry is common. Breaking changes (column removal, type change) require careful migration planning.

H: What about the transactional outbox pattern?

A: Write business data and outbox event in same transaction. Separate process reads outbox, publishes to message queue, marks as published. Guarantees: if transaction commits, event will eventually be published. Handle: polling interval, cleanup of published records, ordering guarantees.

H: How do we maintain ordering guarantees through the CDC pipeline?

A: Partition by entity ID to maintain per-entity ordering. Single partition = total order but limited throughput. Multiple partitions = higher throughput but only per-key ordering. For cross-entity ordering: use logical timestamps or sequence numbers that consumers can use to detect and handle out-of-order delivery.

H: What monitoring is critical for CDC pipelines?

A: Lag between database change and downstream availability. Replication slot growth (PostgreSQL) - growing means consumer is behind. Schema change events. Failed transformations. Also: end-to-end latency tests with synthetic changes, and data consistency checks between source and sink.
