HUMAN: We're implementing a graph database. What are the key differences in storage engines compared to relational databases?

A: Graph storage optimized for traversals. Two approaches: native graph storage (nodes store direct pointers to adjacent nodes - O(1) edge traversal), or graph layer on relational/document store (join-heavy, less efficient traversals but familiar infrastructure). Index-free adjacency is the key native advantage.

H: How does index-free adjacency work?

A: Each node physically stores pointers to its edges, each edge stores pointers to its nodes. Traversing edge is pointer dereference, not index lookup. Cost is O(1) per edge regardless of graph size. Traditional index approach: edge table lookup is O(log n) per hop.

H: What about graph partitioning for distributed graphs?

A: Graph partitioning is hard - minimize cross-partition edges while balancing partition sizes. Approaches: hash by node ID (random, many cross-partition edges), or domain-aware partitioning (users in same region together). Cross-partition traversals need network hops - expensive.

H: How do we optimize for common graph query patterns?

A: Precompute: shortest paths between hot node pairs, k-hop neighborhoods, graph metrics (PageRank, centrality). Caching: recently traversed subgraphs. Query optimization: choose traversal direction (start from lower-degree end), use bidirectional BFS for shortest path.

H: What indexes do graph databases need beyond adjacency?

A: Node property indexes: find starting nodes by property value (like relational). Full-text indexes for text properties. Edge type indexes: filter edges by type during traversal. Composite indexes: property combinations. Consider: covering indexes to avoid node/edge lookups.
