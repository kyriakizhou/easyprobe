HUMAN: We're implementing a distributed search engine. How do we handle index sharding and query routing?

A: Sharding strategies: by document hash (even distribution), by time (for logs), or by some dimension (tenant, category). Query routing: broadcast to all shards, aggregate results. Scatter-gather pattern. Optimization: filter shards if query can be routed, use approximate top-k in shards.

H: How do we handle relevance scoring across shards?

A: Challenge: TF-IDF and BM25 need corpus-wide statistics. Options: local statistics per shard (approximation, usually good enough), global statistics synchronized periodically, or two-phase query (gather stats, then score). For most use cases, local statistics with shard balancing works well.

H: What about the scatter-gather performance with many shards?

A: Latency = slowest shard. Solutions: timeouts with partial results, replica routing to fastest, hedged requests (send to multiple replicas, take first response). Also: merge incrementally as results arrive, not after all complete. Monitor: per-shard latencies, tail latency.

H: How do we handle index updates while serving queries?

A: Segment-based architecture: immutable segments plus small in-memory buffer. Periodic segment merges. Queries search all segments. Updates: add to buffer, flush to new segment, async merge. Deletes: mark deleted in separate structure, filter at query time, remove on merge.

H: What's the replication strategy for search indexes?

A: Options: replicate document writes and index locally (each replica builds index), or replicate indexed segments. Segment replication is more efficient, but replicas can lag. For real-time search: local indexing. For batch-built indexes: segment replication with periodic full rebuilds.
