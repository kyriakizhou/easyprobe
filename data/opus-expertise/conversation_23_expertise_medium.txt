HUMAN: I'm building a multi-tenant SaaS application. How should I structure the database to isolate tenant data?

A: Three main approaches. Separate database per tenant: strongest isolation but operationally complex. Shared database with separate schemas per tenant: good balance for moderate tenant counts. Shared tables with tenant_id column: simplest, most cost-effective, but requires careful query patterns to prevent data leaks.

H: We expect hundreds of tenants eventually. Separate databases for each seems like a lot.

A: For hundreds of tenants, shared database with tenant_id is typically the right choice. You get economy of scale - one connection pool, one migration process, simpler backups. The key is ensuring every query includes the tenant filter. Row-level security in PostgreSQL can enforce this at the database level.

H: How do I prevent developers from accidentally forgetting the tenant filter?

A: Multiple layers. Application layer: use an ORM scope or repository pattern that automatically adds tenant_id to all queries. Database layer: PostgreSQL Row Level Security policies reject queries missing the tenant context. Code review and testing: specifically test for cross-tenant access.

H: What about tenant-specific customizations? Some want custom fields or workflows.

A: For custom fields, use a JSONB column on the main tables. It's schema-flexible per tenant without schema changes. For complex customizations, consider a feature flag system per tenant or a configuration table. Avoid code branches per tenant - that becomes maintenance hell.

H: How should I handle tenant provisioning and onboarding?

A: Automate it fully. Tenant signup creates a row in the tenants table, generates their subdomain or identifier, seeds initial data (admin user, default settings), and optionally triggers welcome workflows. Build admin tools for your team to manage tenants - usage stats, billing, support access.

H: What about performance isolation? One tenant shouldn't slow down others.

A: Rate limiting per tenant protects against noisy neighbors. Monitor per-tenant metrics. For high-value tenants, consider dedicated resources or priority queuing. Query timeouts prevent runaway queries. The shared model has less isolation than separate databases - it's a trade-off you accept for operational simplicity.
