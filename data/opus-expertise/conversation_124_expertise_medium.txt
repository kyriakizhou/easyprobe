HUMAN: How do I implement proper caching strategies for my API?

A: Multiple caching layers: CDN/edge, application-level (Redis), HTTP caching (Cache-Control headers). Cache what's read-heavy and changes slowly. Consider cache invalidation strategy upfront - it's the hard part.

H: When should I use HTTP caching versus application caching?

A: HTTP caching (CDN, browser): public responses that are the same for all users. Cache-Control headers tell browsers/CDNs how long to cache. Application caching (Redis): computed results, database query results, per-user data. Both can work together.

H: What Cache-Control headers should I use?

A: For static assets: Cache-Control: public, max-age=31536000, immutable (with hashed filenames). For API responses: Cache-Control: private, max-age=60 (or appropriate TTL). no-cache means revalidate, no-store means don't cache at all.

H: How do I invalidate cache when data changes?

A: Strategies: time-based expiration (simplest, allows staleness), explicit invalidation (delete keys on updates, requires tracking dependencies), versioned keys (include data version, old keys naturally expire). Choose based on staleness tolerance.

H: What about cache stampede when popular items expire?

A: When cache expires, many requests hit the database simultaneously. Solutions: lock during regeneration (others wait or get stale data), probabilistic early expiration (random items expire earlier), or background refresh before expiration.

H: How do I know what to cache?

A: Profile your application. Cache high-read, low-write data. Cache expensive computations. Monitor cache hit rates - low hit rate might mean poor key design or overly short TTL. Don't cache everything - caching adds complexity and memory usage.
