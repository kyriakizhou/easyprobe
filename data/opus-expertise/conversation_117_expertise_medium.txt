HUMAN: How do I implement data pagination efficiently for a large dataset?

A: Three main approaches: offset-based (LIMIT/OFFSET), cursor-based (keyset), and seek method. Offset is simple but slow at high offsets. Cursor-based scales better. Choose based on your UX needs and data size.

H: Why does offset pagination get slow?

A: OFFSET 100000 LIMIT 20 still scans 100,020 rows, discarding the first 100,000. Database does work just to throw results away. At page 5000, queries become very slow. Also, data changes between requests cause items to shift, causing missed or duplicate items.

H: How does cursor-based pagination work?

A: Instead of "page 5", use "items after cursor X". Cursor encodes the last item's sort values. Query becomes WHERE id > 12345 ORDER BY id LIMIT 20. Uses index efficiently regardless of how deep in the dataset you are.

H: What should the cursor contain?

A: The sort column value(s) for the last item. For simple ID sorting, just the ID. For created_at sorting, include both timestamp and ID (for tiebreaking). Base64 encode to make it opaque - clients shouldn't construct cursors themselves.

H: How do I handle sorting with cursor pagination?

A: Cursor must match sort order. Changing sort mid-pagination doesn't work - client starts over. For multi-column sorts, include all columns in cursor. This is why cursor pagination is more constrained than offset - tradeoff for performance.

H: What metadata should I return with paginated results?

A: Return: next_cursor (null if no more pages), has_more boolean, optionally items per page. Avoid total count for large datasets - it requires a separate COUNT query. If needed, cache or estimate it rather than computing every request.
