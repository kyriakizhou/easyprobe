HUMAN: We need to implement a distributed lock manager for coordination across services. Redis vs etcd vs ZooKeeper - what are the tradeoffs?

A: Redis (Redlock): simple, fast, but contentious - see Martin Kleppmann's critique. No strong consistency guarantees under network partitions. etcd: strong consistency via Raft, designed for coordination, but higher latency. ZooKeeper: battle-tested, ephemeral nodes for locks, but operational complexity. Choice depends on consistency requirements.

H: We need locks for preventing duplicate processing of jobs. Occasional double-processing is acceptable.

A: For best-effort locking, Redis is fine. Use SET with NX and PX (expiration). Release with Lua script checking owner. Accept that in rare cases (network partition, GC pause extending beyond TTL), lock might be violated. Much simpler than consensus-based systems.

H: What about Redlock - isn't that supposed to solve Redis's consistency issues?

A: Redlock attempts distributed consensus across multiple Redis instances. The critique: clock drift and process pauses can still violate safety. For coordination where correctness matters, etcd/ZooKeeper are safer. For performance-critical best-effort locking, single Redis node is simpler and probably just as good.

H: If we go with etcd, how do we implement a distributed lock?

A: etcd has built-in lock API via etcd-client. Create a lease (TTL), attach to a key. Client keeps lease alive with heartbeats. If client dies, lease expires, lock releases. For manual implementation: transactions with revision checking for CAS operations.

H: How do we handle the case where a lock holder dies while holding the lock?

A: With any system: TTL/lease expiration automatically releases orphaned locks. Set TTL appropriate to your operation duration plus buffer for GC pauses. Renew lease during long operations. On etcd/ZK, ephemeral nodes disappear when session ends, natural cleanup.

H: What about fencing tokens to detect stale lock holders?

A: Essential for correctness. Lock acquisition returns an incrementing token. All protected operations include the token. Resource validates token is current before accepting operation. If old holder wakes up with stale token, resource rejects. etcd and ZK support this pattern naturally.
