HUMAN: How do I properly handle sensitive data like API keys and database credentials?

A: Never commit secrets to git. Use environment variables for runtime secrets. Use secrets managers (AWS Secrets Manager, Vault) for production. Encrypt at rest. Limit access - not everyone needs production credentials. Rotate regularly.

H: What about local development? How do developers get secrets?

A: .env files for local development (gitignored). .env.example documents required variables without values. For shared secrets, use a team password manager (1Password, Bitwarden) or internal secrets store. Each developer can have their own API keys when possible.

H: How do I prevent secrets from leaking into logs?

A: Sanitize logs - redact patterns that look like secrets. Never log request bodies without filtering. Use structured logging and filter sensitive fields. Review log output periodically. Consider tools that scan for secrets in logs.

H: What if a secret gets accidentally committed to git?

A: The secret is compromised - rotate it immediately. Remove from git history using git filter-branch or BFG Repo-Cleaner. But assume it's been seen - anyone who cloned the repo has it. The rotation is the critical step.

H: How do I handle secrets in CI/CD?

A: Use CI platform's secret management (GitHub Secrets, GitLab CI variables). Never echo secrets in logs. Mask them in output. Access secrets only in the steps that need them. Prefer short-lived credentials using OIDC when possible.

H: How often should I rotate secrets?

A: Depends on sensitivity. Database passwords: quarterly or when team changes. API keys: annually or on suspected compromise. Some secrets can auto-rotate (AWS RDS passwords). Have a rotation procedure documented so it's not an emergency scramble.
