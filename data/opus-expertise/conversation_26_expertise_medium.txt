HUMAN: We're having issues with database migrations in our team. Sometimes deployments fail because migrations are inconsistent.

A: Migration conflicts often stem from workflow issues. Common problems: developers creating migrations on branches that later conflict, manual database changes not captured in migrations, environment drift between development and production. What's your current migration workflow?

H: Each developer has a local database. They create migrations, test locally, and merge to main. Deployments run migrations automatically.

A: That's a reasonable setup. The issues are likely: multiple developers adding migrations without coordination (version conflicts), migrations that work locally but fail in production (different data), or migrations that pass CI but conflict when merged together.

H: We had a case where two developers added migration 47 on different branches.

A: Use timestamped migration names instead of sequential numbers - 20240115143022_add_user_email.sql. This prevents conflicts since timestamps are unique. Most migration tools support this. Also consider squashing old migrations periodically to reduce complexity.

H: What about migrations that take forever on large production tables?

A: Long-running migrations are dangerous - they can lock tables and cause downtime. Strategies: add columns as nullable first, backfill in batches, then add constraints; create new indexes concurrently (PostgreSQL supports this); use pt-online-schema-change for MySQL.

H: How do we test migrations before deploying to production?

A: Have a staging environment with production-like data volume. Run migrations there first. For destructive migrations, take a database backup before production deployment. Consider a "dry run" step that validates migration syntax. Some teams restore production snapshots to test against.

H: What about rollbacks? Should every migration have a down migration?

A: Controversial topic. Some say always have down migrations for rollback capability. Others say they're rarely used and add complexity - you'll likely roll forward with a fix anyway. At minimum, have down migrations for simple structural changes; complex data migrations might be one-way.
