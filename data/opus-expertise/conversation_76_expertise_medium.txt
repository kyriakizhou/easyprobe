HUMAN: How do I design a good database schema for a new application?

A: Start with domain modeling. Identify entities (users, orders, products), their attributes, and relationships. Normalize to reduce redundancy - usually 3rd normal form is sufficient. Consider query patterns when making tradeoffs. Document your schema and reasoning.

H: How do I decide between one-to-many and many-to-many relationships?

A: Ask the real-world question. Can a book have multiple authors? Can an author write multiple books? If both answers are yes, it's many-to-many (needs join table). If only one side can have multiple, it's one-to-many (foreign key on the "many" side).

H: When should I denormalize?

A: When read performance matters more than write complexity. Common cases: storing computed values (order total), duplicating frequently-joined data (user name on every post), or caching complex aggregations. Track denormalized data carefully - updates need to sync multiple locations.

H: How do I handle soft deletes?

A: Add deleted_at timestamp column, null means active. Queries must include WHERE deleted_at IS NULL. Consider using database views to abstract this. Alternatively, move deleted rows to archive tables. Be aware: soft deletes complicate unique constraints and foreign keys.

H: What data types should I use?

A: Use appropriate types: UUID or BIGINT for IDs, TEXT over VARCHAR (PostgreSQL), TIMESTAMP WITH TIME ZONE for dates, BOOLEAN not integers for flags, JSONB for semi-structured data. Avoid stringly-typed data where specific types exist. Store monetary values as NUMERIC, not float.

H: How do I handle schema changes once the database has data?

A: Migrations! Tools like Flyway, Liquibase, or ORM migrations (Prisma, Knex). Each change is a versioned migration script. Apply in order on each environment. Make migrations reversible when possible. Test migrations with production-like data before deploying.
