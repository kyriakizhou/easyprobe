HUMAN: How do I implement proper data archiving for old records?

A: Archiving moves old data to cheaper storage, keeping main tables small and fast. Options: move to archive tables, export to cold storage, or partition tables. Maintain referential integrity. Keep retrieval possible when needed.

H: When should I archive versus delete?

A: Archive: regulatory requirements, potential future need, audit trails. Delete: truly no longer needed, privacy requirements (GDPR). Some data needs both: archive for N years, then delete. Document retention policies.

H: How do I implement archiving in PostgreSQL?

A: Create archive tables with same structure. Move old rows: INSERT INTO orders_archive SELECT * FROM orders WHERE created_at < '2022-01-01'; DELETE FROM orders WHERE created_at < '2022-01-01'. Do in batches to avoid long locks. Run during low traffic.

H: What about foreign key relationships?

A: Tricky. Options: archive related records together, allow orphaned references in archives (foreign key to archived table), or denormalize archived data (store full record, not just IDs). Plan based on retrieval needs.

H: How do I query archived data when needed?

A: For occasional access: UNION with archive tables or search archive separately. For transparent access: partitioned tables (current and old partitions). For rare access: restore from backup or cold storage. Balance query convenience against storage cost.

H: Should I use table partitioning instead?

A: Partitioning keeps data in one logical table but physical partitions can be managed separately. Old partitions can be moved to cheaper storage. Queries automatically check relevant partitions. Better for time-series data that's frequently queried by date.
