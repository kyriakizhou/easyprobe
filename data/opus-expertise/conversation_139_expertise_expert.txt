HUMAN: We're implementing a data pipeline with exactly-once semantics end-to-end. What are all the components that need to participate?

A: End-to-end exactly-once: every component must participate. Source: must track position (offset, timestamp) and replay from position. Processing: must checkpoint state with input position atomically. Sink: must handle duplicates (idempotent write) or participate in two-phase commit. Any gap breaks the guarantee.

H: How does Kafka's exactly-once work internally?

A: Kafka exactly-once: idempotent producers (sequence numbers), transactional producers (atomic multi-partition writes), and exactly-once streams (read-process-write atomically). Under hood: two-phase commit, transaction coordinator, transaction log. Consumer: read_committed isolation.

H: What about exactly-once with external systems?

A: External system must support idempotency or transactions. Idempotent: write with unique key, overwrite is safe. Transactional: two-phase commit (start transaction, write, commit if processing commits). If neither: document the at-least-once guarantee, design downstream for duplicates.

H: How do we handle exactly-once across different technologies?

A: Cross-technology: often can't achieve exactly-once. Practical approach: at-least-once delivery + idempotent sinks + deduplication. Example: Kafka → Flink → PostgreSQL. Flink checkpoints Kafka offsets + processing state. PostgreSQL: upsert with message ID. Late duplicates: dedup at read time.

H: What monitoring proves exactly-once is working?

A: Compare source count with sink count (should match). Track duplicate detection rate at sink (should be low). Verify checkpoint coverage (no gaps). Monitor transaction commit latency. Test: inject failures, verify no duplicates or loss after recovery.
