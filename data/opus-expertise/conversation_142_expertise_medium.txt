HUMAN: How do I implement proper data migration when changing database schema?

A: Migrations are versioned scripts that change database schema incrementally. Run in order, tracked in database. Support both up (apply) and down (rollback). Use migration tools: Prisma Migrate, Knex, Flyway, or ORM-specific tools.

H: What should go in a migration?

A: Schema changes: create/alter/drop tables, add/remove columns, create indexes, add constraints. Keep migrations focused - one logical change per migration. Name descriptively: 001_create_users_table, 002_add_email_index.

H: How do I handle data migrations alongside schema migrations?

A: Separate when possible. Schema migrations: alter structure. Data migrations: transform existing data. Some tools have separate concepts. If combined, be careful with large tables - data transformations can be slow and lock tables.

H: How do I write migrations that don't cause downtime?

A: Avoid exclusive locks on large tables. Add columns as nullable first. Create indexes concurrently (PostgreSQL: CREATE INDEX CONCURRENTLY). Don't rename columns directly - add new, migrate data, remove old. Test migration time with production-like data.

H: What about rollbacks? Should every migration have a down?

A: Down migrations are good for development and testing. In production, forward-only is often safer - fix issues with new migrations. Complex data changes may not be reversible anyway. Have down migrations for simple schema changes.

H: How do I test migrations before production?

A: Apply to staging with production-like data. Time the migration. Verify application works with migrated schema. Have a rollback plan. For risky migrations, practice the rollback. Consider running migration in a read replica first.
