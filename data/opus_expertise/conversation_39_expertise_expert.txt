HUMAN: We're implementing a job scheduling system that needs to handle millions of jobs with precise timing requirements. What's the architecture for achieving sub-second scheduling accuracy at scale?

A: Precise timing at scale requires: distributed timer infrastructure (not single scheduler), partitioned job queues by scheduled time, worker clock synchronization, and handling of scheduling delays. Consider: is true precision needed, or is "approximately on time" acceptable?

H: We need jobs to fire within 1 second of their scheduled time. Occasionally 5-second delays are acceptable, not more.

A: Hierarchical time wheel is efficient for this. Coarse bucket (minutes), fine bucket (seconds) within each minute. Workers pull from current bucket. For scale: partition time wheels across nodes by job ID hash. Each node handles its subset of jobs for any given time.

H: How do we handle worker clock drift?

A: NTP for clock sync. Accept some drift - don't require perfect sync. Use logical time (job sequence) alongside wall time. If job scheduled for T=100s and current time is T=99s, wait. If T=101s, fire immediately (already late). Monitor clock skew across workers.

H: What about jobs scheduled far in the future? We have jobs scheduled months ahead.

A: Don't load far-future jobs into memory. Store in database with scheduled_at index. Loader process periodically queries for jobs approaching their window (next hour, next day). Loads into hot scheduling system. Far-future updates go to database, caught by next load.

H: How do we handle job rescheduling or cancellation?

A: Cancellation: remove from time wheel if present, mark cancelled in database. Rescheduling: cancel and re-add. Challenge: job might already be dispatched when cancel arrives. Include job version - worker checks version before executing, skips if stale.

H: What about handling a worker going down with jobs in progress?

A: Lease-based execution. Worker takes lease on job, heart beats. If heartbeat fails, lease expires, job is rescheduled. Set lease duration appropriately - long enough for normal execution, short enough for fast failure detection. Track in-progress jobs in distributed store.
