HUMAN: How do I handle environment-specific behavior in my application?

A: Use environment variables and configuration layers. Never hardcode environment-specific values. Common pattern: default config < environment config < environment variables. Check NODE_ENV or similar to determine environment. Use different .env files for different environments.

H: What values typically differ between environments?

A: Database URLs, API endpoints, feature flags, logging levels, third-party service keys (sandbox vs production), rate limits, cache TTLs. Anything that should behave differently in development, staging, and production.

H: How do I manage .env files across environments?

A: .env.example committed (documents required vars, no secrets), .env.local for local dev (gitignored), environment-specific .env.production, .env.staging. In production, inject via platform (Heroku config, AWS Parameter Store, Kubernetes secrets).

H: Should I validate environment variables?

A: Yes! Fail fast on startup if required variables are missing. Use libraries like envalid (Node.js) to validate types and required values. Surface clear errors: "DATABASE_URL is required but not set" is better than cryptic failures later.

H: How do I handle feature differences between environments?

A: Feature flags controlled by environment. IS_PRODUCTION check for certain behaviors. But minimize environment-specific code paths - they're hard to test. Prefer: same code everywhere, different configuration. Log environment on startup for debugging.

H: What about local development with production-like settings?

A: Sometimes useful to test with production config locally. Never use real production secrets locally. Create a "production-like" local profile with similar settings but local resources. Test staging environment that mirrors production config.
