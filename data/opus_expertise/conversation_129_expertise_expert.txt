HUMAN: We're implementing a distributed message deduplication system. What are the trade-offs between different approaches?

A: Deduplication approaches: message ID tracking (store seen IDs, reject duplicates), idempotency keys (client provides key, server deduplicates), or idempotent operations (operations naturally handle duplicates). Trade-off: storage for tracking vs application complexity.

H: How do we scale message ID tracking?

A: Store message IDs with TTL (duplicates only matter within a window). Bloom filter: space-efficient, false positives acceptable (reprocess rather than dedupe). Partitioned storage: shard ID storage by message ID hash. Consider: how long can duplicates arrive after original?

H: What about exactly-once delivery with message ID tracking?

A: Not quite exactly-once - it's at-least-once delivery with at-most-once processing. Producer sends with ID, broker deduplicates on receive. Consumer processes with ID, application layer deduplicates side effects. End-to-end exactly-once requires all components participating.

H: How do we handle duplicates that arrive much later?

A: Late duplicates after ID expired from tracking. Options: accept rare duplicates (application handles), longer TTL (more storage), or permanent ID storage (expensive). Usually: design for idempotent processing as defense in depth, short TTL catches most duplicates.

H: What's the idempotency key pattern?

A: Client generates unique key per logical operation. Server: check if key seen, if yes return cached response, if no execute and cache. Client: retry with same key on failure. Server tracks: key → result mapping with TTL. Ensures: same logical operation produces same result.
