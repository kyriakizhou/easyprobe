HUMAN: We're implementing a service mesh data plane. What are the key proxy behaviors we need to implement?

A: Core functions: traffic routing (based on headers, paths, weights), load balancing, circuit breaking, retries with backoff, timeouts, and observability (metrics, traces, access logs). Also: mTLS for service-to-service encryption, and health checking of upstreams.

H: How does the proxy handle connection pooling to upstreams?

A: Pool per upstream service, respect HTTP/2 multiplexing. Limits: max connections per host, max pending requests, max requests per connection. On limit reached: queue with timeout or fail fast. Connection lifecycle: idle timeout, max lifetime, health checks.

H: What's the circuit breaker state machine?

A: Three states: closed (normal), open (failing fast), half-open (testing). Closed → open: when error threshold exceeded in window. Open: all requests fail immediately. After timeout, transition to half-open. Half-open: allow one request. If succeeds → closed, if fails → open.

H: How do we implement retry policies correctly?

A: Retry budget: max retries per request, and cluster-wide retry ratio limit. Only retry on retriable errors (5xx, connection errors, not 4xx). Backoff: exponential with jitter. Headers: propagate retry count, let upstream track. Important: retry amplification can cause cascading failures.

H: What observability does the proxy provide?

A: Per-request: latency histogram, status codes, request size. Per-upstream: connection count, pending requests, health status. Traces: inject/propagate trace headers, report spans. Access logs: selectable fields, sampling for high-volume. Expose via Prometheus endpoint or push to collector.
