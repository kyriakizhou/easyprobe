HUMAN: We're implementing a CRDT-based collaborative editor. What are the key data structure choices?

A: CRDTs for text: sequence CRDTs like LSEQ, RGA, or Yjs. Each character has unique ID, position determined by IDs of neighbors. Concurrent insertions at same position resolved deterministically. Trade-offs: memory overhead of IDs, performance of position calculation, tombstone accumulation.

H: How do we handle deletions in sequence CRDTs?

A: Tombstones: mark deleted, don't remove. Required because concurrent operations might reference deleted element. Problem: tombstones accumulate forever. Solutions: garbage collection when all replicas have seen delete, or CRDT designs with bounded tombstones. Yjs uses efficient tombstone compression.

H: What about rich text formatting?

A: Formatting as marks with start/end anchors, or formatting as overlays on character ranges. Concurrent formatting: might create overlapping bold ranges (merge), or conflicting font size (last-writer-wins per attribute). Peritext research paper addresses many edge cases.

H: How do we handle cursor positions and selections?

A: Relative positions: cursor position = reference to character ID, not index. On concurrent inserts before cursor, cursor stays relative to same character. Selections: start and end relative positions. Share cursors with other users for collaboration awareness.

H: What's the network architecture for syncing edits?

A: Options: central server (simpler, server is authoritative ordering), or peer-to-peer (more resilient, complex). Hybrid: peer-to-peer when online, queue ops for server sync. Compression: batch operations, delta encoding. Consider: offline support, conflict resolution visibility.
