HUMAN: I'm trying to improve our API design. We're using REST but it feels inconsistent. Any best practices?

A: Consistency is key in API design. Start with uniform URL patterns: plural nouns for resources (users, orders), nested resources where it makes sense (users/123/orders). Use HTTP methods correctly - GET reads, POST creates, PUT/PATCH updates, DELETE removes. Return appropriate status codes.

H: We have some endpoints like /getUserOrders and /createUser. That's not RESTful?

A: Those are RPC-style, not REST. RESTful would be GET /users/{id}/orders and POST /users. The resource is the noun, the HTTP method is the verb. This gives you predictable patterns - clients know how to interact with any resource type.

H: What about operations that don't fit CRUD? Like "send password reset email"?

A: Good question - this trips people up. Options: POST to a sub-resource (POST /users/{id}/password-reset-emails), use a "commands" endpoint (POST /commands/reset-password), or be pragmatic with action endpoints (POST /users/{id}/reset-password). Pure REST is a guideline, not dogma.

H: How should I handle errors consistently?

A: Define a consistent error format: {"error": {"code": "VALIDATION_FAILED", "message": "Human readable message", "details": [...]}}. Use appropriate HTTP status codes: 400 for bad requests, 401 unauthorized, 403 forbidden, 404 not found, 422 for validation errors. Don't return 200 with error in the body.

H: Should I version my API?

A: Yes, from the start. URL versioning (/v1/users) is most common and explicit. Header versioning is cleaner but less visible. Plan for how you'll deprecate old versions. Breaking changes go in new versions; additive changes can go in existing versions.

H: Any thoughts on request/response formats?

A: Use JSON consistently. Use camelCase for property names (JavaScript convention). Return useful metadata - pagination info, timestamps, self-links. Consider envelope patterns ({"data": [...], "meta": {...}}) vs flat responses. Whatever you choose, be consistent.
