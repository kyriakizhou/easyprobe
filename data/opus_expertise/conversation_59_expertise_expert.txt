HUMAN: We're designing a query optimizer for our analytical database. What are the key components?

A: Core components: parser (SQL to AST), analyzer (resolve names, check types), logical planner (relational algebra), optimizer (transform and cost), physical planner (choose algorithms). Optimizer is typically rule-based (heuristics) plus cost-based (statistics and cost model). Cascades framework is influential.

H: How do we estimate cardinality for complex predicates?

A: Single column: histograms (equi-width, equi-depth, or compressed). Multiple columns: assume independence (often wrong), use multi-dimensional histograms, or sample-based estimation. For complex expressions: use query feedback to learn from actual cardinalities. Errors compound - 2x error per join becomes 8x after 3 joins.

H: What heuristic rules should we apply before cost-based optimization?

A: Push predicates down, push projections down (reduce columns early), simplify expressions, eliminate redundant operations, flatten subqueries when possible, reorder predicates by selectivity. These are almost always beneficial and reduce the search space for cost-based optimization.

H: How do we choose join algorithms?

A: Hash join: good for equality joins, builds hash table on smaller side. Sort-merge: good when inputs are sorted or order needed downstream. Nested loop: when inner side is indexed or very small. Index nested loop: for highly selective joins. Cost model considers: build vs probe costs, memory limits, I/O patterns.

H: What about query plan caching?

A: Cache plans keyed by normalized query (literals replaced with placeholders). Invalidate on schema changes or significant statistics changes. Challenge: bind variable peeking - optimal plan depends on actual parameter values. Solutions: adaptive plans, multiple cached plans per query, or re-optimize on parameter change.
