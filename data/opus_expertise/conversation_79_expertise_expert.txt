HUMAN: We're implementing a feature flag system for gradual rollouts. What are the consistency requirements?

A: Consistency trade-offs: strong consistency ensures all users see same flags (simpler reasoning), eventual consistency allows local caching (lower latency). For rollouts: eventual is usually fine, percentages are approximate anyway. For kill switches: need faster propagation, consider push mechanism.

H: How do we implement sticky bucketing for percentage rollouts?

A: Hash user ID + flag name → bucket (0-100). User always gets same bucket for same flag. Advantages: consistent experience across sessions, A/B test validity. Implementation: deterministic hash, store user's bucket if needed for later analysis. Handle: new users, anonymous users.

H: What about targeting rules and their evaluation order?

A: Rules evaluated in priority order. First match wins. Rule types: user list (exact match), segment (attribute-based), percentage. Example priority: 1) kill switch (all off), 2) allowlist (specific users), 3) segment rules, 4) percentage rollout, 5) default. Store rules efficiently for fast evaluation.

H: How do we handle flag dependencies?

A: Flag A requires flag B enabled. Options: explicit dependency declaration (system enforces), or document-only (developer responsibility). Enforcement: on flag change, check dependencies, warn or prevent inconsistent states. Graph of dependencies - detect cycles.

H: What observability is needed for feature flags?

A: Per-flag: evaluation counts, value distribution, error rate. Per-user: active flags (for debugging). Time-series: flag changes over time, rollout percentage changes. Correlation: flag exposure with business metrics. Audit log: who changed what when.
