HUMAN: We're implementing a write-ahead log (WAL) for our database. What are the key design decisions for durability vs performance?

A: Core trade-offs: fsync frequency (every commit vs batched), log format (physical vs logical), and group commit. Physical logging records page images, logical records operations. Group commit batches multiple transactions' fsyncs together, amortizing the disk latency.

H: How does group commit work exactly?

A: Transactions write to log buffer, mark themselves waiting for commit. A dedicated thread periodically fsyncs the log and wakes all waiting transactions. Or: first waiter becomes the leader, waits briefly for more transactions, then fsyncs for the group. Latency increases slightly, throughput improves dramatically.

H: What's the difference between redo-only and undo-redo logging?

A: Redo-only (ARIES-style with steal/no-force): log contains redo information, dirty pages can be flushed before commit, undo via compensation log records. Undo-redo: log contains both, simpler but more log volume. Redo-only is more common in modern systems.

H: How do we handle log file management - rotation and archival?

A: Checkpoint determines oldest needed log record. Log files before that can be archived/deleted. For point-in-time recovery, archive all logs. Implement log rotation at size boundaries. Keep file sizes manageable for efficient archival and potential replay.

H: What about log compression?

A: Trade-off: CPU for compression vs I/O bandwidth. Modern CPUs often make compression worthwhile, especially for logical logging with repetitive patterns. LZ4 is popular for speed. Consider: compress on write (latency) vs background compression of sealed segments.
