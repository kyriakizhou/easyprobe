HUMAN: We're implementing a distributed object store with strong consistency. How do we handle partial failures during write operations?

A: Partial failure: some replicas acknowledge, others don't. Write quorum ensures durability (W > N/2). For linearizability: read quorum must overlap with write quorum (R + W > N). On partial failure: don't acknowledge to client until quorum reached, use timeout + retry, or return error and let client retry.

H: How do we handle conflicting writes from concurrent clients?

A: Options: last-writer-wins (LWW) with timestamps (potential data loss), or conflict detection with resolution. Strong consistency: use consensus for each write, or single leader. Optimistic: detect conflict on read repair, ask client to resolve. CRDTs for specific data types.

H: What's the read repair mechanism?

A: On read, query multiple replicas. If values differ, reconcile and write back correct value. Eager: always read from multiple. Lazy: read from one, async background consistency check. Trade-off: eager catches inconsistencies faster, higher read latency.

H: How do we implement compare-and-swap atomically across replicas?

A: CAS needs consensus. Single leader: leader performs CAS, replicates result. Multi-leader: use Paxos/Raft for the CAS operation. Distributed transaction: prepare phase locks, commit phase applies. Simpler: version numbers on objects, CAS checks version, reject if changed.

H: What happens during network partition between replicas?

A: With strong consistency (CP): minority partition becomes unavailable, majority continues. Client requests to minority fail or redirect. On partition heal: minority catches up from majority. Important: detect partition vs node failure (different responses).
