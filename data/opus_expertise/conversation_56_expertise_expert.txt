HUMAN: We're implementing optimistic concurrency control for our distributed database. How does it compare to pessimistic locking in practice?

A: OCC: read without locks, validate at commit, abort on conflict. Works well for low-contention workloads. Pessimistic: acquire locks upfront, guaranteed success if locks obtained. OCC wastes work on abort, pessimistic wastes time waiting for locks. Hybrid approaches exist.

H: How does validation work in OCC?

A: At commit: verify that all read values haven't changed (read set validation) and no write conflicts with concurrent transactions. Implementation: version numbers on records, or timestamp ordering. Backward validation checks against committed transactions, forward validation checks against active ones.

H: What about write skew anomalies?

A: Write skew: two transactions read overlapping data, make disjoint writes, but combined result violates invariant. Example: both doctors go off-call because each sees the other on-call. Prevention: promote reads to writes (SELECT FOR UPDATE equivalent) or use serializable isolation.

H: How do we handle long-running transactions with OCC?

A: Long transactions are problematic - high abort probability. Options: break into smaller transactions, use saga pattern, or switch to pessimistic for known long operations. Some systems use adaptive approaches - start optimistic, escalate to pessimistic on repeated aborts.

H: What's the implementation complexity difference?

A: OCC is simpler for single-node (no deadlocks, no lock manager). Distributed OCC needs coordination for validation across nodes. Pessimistic requires distributed deadlock detection or timeout-based resolution. Both need careful transaction ordering for serializability.
