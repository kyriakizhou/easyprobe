HUMAN: Our GraphQL API is getting slow. Any optimization strategies?

A: GraphQL has specific performance challenges. Common issues: N+1 queries from nested resolvers, over-fetching large object graphs, expensive field computations, and lack of caching strategy. Let's identify your bottleneck first. Do you have query tracing enabled?

H: Yes, using Apollo Studio. Some queries make hundreds of database calls.

A: Classic N+1 problem. If you fetch 50 users, and each user resolver fetches their posts separately, that's 51 queries. Solution: DataLoader. It batches requests within a single tick - 50 separate user-post requests become one query for all 50 users' posts.

H: We started using DataLoader but still seeing issues with deeply nested queries.

A: Deep nesting compounds the problem. Additional strategies: query complexity analysis (reject overly complex queries), depth limiting, pagination on all list fields, and eager loading at higher levels when you know nested data will be needed. Consider your schema design.

H: What about caching at the GraphQL layer?

A: Multiple caching options. Apollo Server has response caching with cache hints on schema types. Redis can cache resolved objects. CDN caching is tricky since POST requests aren't cached by default, but you can use persisted queries with GET. Consider which data can be stale.

H: Some fields are expensive to compute. How do I only compute them when requested?

A: That's a feature of GraphQL! Only requested fields are resolved. Ensure your resolvers don't compute expensive fields unless asked for. Check the resolver info parameter to see what's being requested. Lazy evaluation and caching within request context helps.

H: How do I prevent clients from requesting too much at once?

A: Implement query complexity analysis. Assign costs to fields (lists might cost 10, scalar fields cost 1). Sum the total cost and reject queries exceeding a limit. Also set max depth limits and timeouts. Libraries like graphql-query-complexity handle this.
