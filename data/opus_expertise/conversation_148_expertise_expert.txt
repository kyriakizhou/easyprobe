HUMAN: We're implementing a distributed throttling system across multiple services. How do we coordinate rate limits?

A: Coordinated throttling: multiple services share rate limit (e.g., API gateway and downstream). Options: centralized counter (accurate, latency), distributed counters with sync (approximate), or token bucket with shared replenishment. Challenge: consistency vs performance.

H: How do we handle rate limit inheritance in service hierarchies?

A: User → Service A → Service B. User has global limit 100 RPS. Should A and B enforce independently? Options: only edge (A) enforces, or B trusts A's enforcement. If B also enforces: might double-count, underutilize limit. Usually: edge enforcement, internal services trust headers.

H: What about dynamic rate limits based on system load?

A: Adaptive throttling: reduce rate limits when system stressed. Signals: CPU usage, queue depth, error rate, latency. Response: progressively reduce limits, prioritize important traffic. Implementation: feedback loop with dampening (avoid oscillation). Communicate: surface rate limit changes to clients.

H: How do we implement fair rate limiting across clients?

A: Fair: each client gets equal share of capacity. Weighted: clients get proportional to weight (tier, payment). Implementation: per-client counters with limits, or weighted fair queuing. Burst handling: allow burst within global headroom, or per-client burst budgets.

H: What monitoring is needed for distributed rate limiting?

A: Per-client: rate of requests, rate limit utilization, rejected count. Global: aggregate rate, rejection rate, capacity utilization. Health: sync lag (local vs global), error rate in rate limiting service. Alert: high rejection rate, sync failures, capacity exhaustion.
