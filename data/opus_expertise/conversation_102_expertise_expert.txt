HUMAN: We're implementing a custom garbage collector. What are the trade-offs between different GC algorithms?

A: GC trade-offs: throughput (application time vs GC time), latency (pause duration), memory overhead (extra space for GC), and implementation complexity. Mark-sweep: simple, fragmentation. Copying: compaction but 2x memory. Mark-compact: best of both but complex. Generational: optimize for common case.

H: How does generational GC exploit object lifetimes?

A: Weak generational hypothesis: most objects die young. Young generation: collected frequently, fast (small, copying). Objects surviving multiple collections promoted to old generation. Old generation: collected less often. Major savings: don't scan long-lived objects repeatedly.

H: What are the challenges with concurrent GC?

A: Concurrent GC: collector runs alongside mutator (application). Challenges: mutator changes object graph during marking (need write barriers), maintaining consistency (snapshot-at-beginning vs incremental update), and synchronization overhead. Goal: minimize stop-the-world pauses.

H: How do write barriers work?

A: Write barrier: code executed on reference write. Snapshot-at-beginning: remember overwritten references (won't miss unmarked objects). Incremental update: mark newly reachable objects. Trade-off: barrier overhead vs floating garbage. Card marking: coarse tracking for old→young references.

H: What metrics indicate GC problems?

A: Allocation rate: high means more collections. Promotion rate: high means young gen too small or object lifetimes middle-aged (worst case). Pause times: P99 matters for latency-sensitive apps. GC CPU: percentage of time in GC. Memory fragmentation. Tune based on actual workload profiles.
