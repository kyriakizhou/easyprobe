HUMAN: How do I design a good API for mobile clients with potentially poor connectivity?

A: Design for unreliable networks. Key principles: offline-first with sync, idempotent operations for safe retries, small response payloads, efficient delta updates, and handling of interrupted requests gracefully. What kind of app is it?

H: A social app with feeds, posts, and messaging.

A: Core strategies: return essential data first (text, then images), support pagination with cursors (not offsets) for consistent paging, provide delta endpoints (posts since timestamp X), and allow offline composition of posts that sync when online.

H: How do I handle conflicting offline edits?

A: Conflict resolution strategies: last-write-wins (simplest, sometimes loses data), server-wins (server is source of truth), client-wins (user intent preserved), or merge (complex but complete). For social content, last-write-wins or manual user resolution is usually acceptable.

H: What about requests that get interrupted mid-flight?

A: Idempotency keys. Client generates unique ID for each operation, sends with request. If request fails, retry with same ID. Server checks if operation already completed. For creates, store the ID until confirmed. For reads, standard caching and retries work.

H: Should I compress API responses?

A: Yes, gzip or brotli compression significantly reduces transfer size. Most HTTP clients and servers handle this automatically with Accept-Encoding headers. Consider also: Protocol Buffers or MessagePack instead of JSON for even smaller payloads, though JSON is more debuggable.

H: What about images and media?

A: Serve multiple resolutions. Mobile gets smaller images by default. Support progressive loading (low-quality placeholder first). Use efficient formats like WebP. Consider lazy loading for feed content. CDN distribution critical for media. Cache aggressively on device.
