HUMAN: I'm building a REST API that needs to serve both mobile apps and a web frontend. Any considerations?

A: Multi-client APIs need to balance flexibility with simplicity. Key considerations: consistent response formats, versioning strategy, authentication that works across platforms, handling different bandwidth/latency constraints for mobile, and feature parity decisions.

H: Mobile has bandwidth limitations. Should I create separate endpoints for mobile?

A: Avoid separate endpoints - creates maintenance burden. Better approaches: sparse fieldsets (let clients request only needed fields), different compression (gzip/brotli), image resizing on-the-fly, and pagination with smaller default limits for mobile. GraphQL also naturally addresses this.

H: What about authentication? Web uses cookies but mobile typically uses tokens.

A: Support both. The same JWT token can be in a cookie for web (with CSRF protection) or Authorization header for mobile. Or use a single approach - many web apps now use Authorization headers too, avoiding CSRF complexity. Just ensure secure token storage on all platforms.

H: How do I handle API versioning when mobile apps can't force users to update?

A: This is critical. Version in URL (/v1/users) or header. Support old versions for extended periods - mobile apps in app stores may be years old. Deprecation policy: announce, give warning period, monitor usage of old versions before sunset. Use feature flags for gradual rollouts.

H: What about offline support for mobile?

A: Design for offline at the API level: include timestamps for sync, support conflict resolution (last-write-wins or merge strategies), idempotent operations for safe retries, and delta sync endpoints if practical. Mobile apps cache responses and queue writes.

H: Should I use REST or GraphQL for this use case?

A: Both can work. GraphQL's flexibility (clients request exact fields) naturally addresses mobile bandwidth concerns. REST is simpler, more cacheable at HTTP layer. Consider team familiarity. For most apps, well-designed REST is sufficient. GraphQL shines for complex, varied data requirements.
