HUMAN: I need to implement password hashing in my application. What algorithm should I use?

A: Use bcrypt, Argon2, or scrypt - these are designed for password hashing. Never use MD5, SHA-1, or SHA-256 for passwords - they're too fast, making brute force attacks feasible. Password hashing should be deliberately slow to make attacks expensive.

H: What's special about bcrypt compared to regular hashing?

A: Bcrypt has a configurable "cost factor" that controls how slow it is. As computers get faster, you increase the cost. It also automatically handles salting - each hash includes a unique salt, so identical passwords produce different hashes. This prevents rainbow table attacks.

H: What cost factor should I use for bcrypt?

A: Choose a cost where hashing takes 250-500ms on your production hardware. Start with 10-12 and measure. Higher is more secure but slower. Balance security against login latency and DoS potential (expensive hashing can be exploited for CPU exhaustion).

H: How do I verify a password later?

A: Use the library's compare function (bcrypt.compare in most implementations). It extracts the salt and cost from the stored hash, applies them to the input password, and compares. Never try to decrypt the hash - hashing is one-way by design.

H: What about Argon2? I've heard it's better.

A: Argon2 won the Password Hashing Competition. It's considered state-of-the-art with tunable memory, time, and parallelism parameters. The memory-hard design resists GPU attacks. Adoption is growing but bcrypt has more widespread support. Either is a good choice over older methods.

H: How should I store the hash in the database?

A: Store the full hash string that includes algorithm identifier, cost, salt, and hash - typically 60-100 characters. Use a VARCHAR(255) to be safe for future algorithm changes. Consider adding a password_updated_at timestamp for policies like forced reset after N months.
