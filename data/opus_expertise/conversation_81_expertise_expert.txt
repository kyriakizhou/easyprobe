HUMAN: We're implementing a distributed queue with exactly-once processing semantics. What are the implementation challenges?

A: Exactly-once is actually "effectively once" - at-least-once delivery + idempotent processing. Components: durable message storage, consumer acknowledgment, deduplication (message ID tracking), and transactional processing (consume + side effect atomically).

H: How do we implement the deduplication?

A: Track processed message IDs with TTL. Before processing, check if seen. Challenges: ID storage grows with throughput, need efficient lookup. Bloom filter for fast negative check, persistent store for positives. Alternative: make processing naturally idempotent (upserts, not inserts).

H: What about ordering guarantees with exactly-once?

A: Ordering + exactly-once is harder. If message fails, do we skip it (breaks ordering) or block (reduces availability)? Solutions: per-key ordering only (partition by key), or dead-letter queue for poison messages with manual intervention. Document the ordering guarantees clearly.

H: How do we handle consumer failures during processing?

A: Visibility timeout: message invisible to other consumers during processing. If not acked within timeout, becomes visible again. Challenge: original consumer might still be processing (slow, not dead). Solution: shorter timeout + renewal heartbeat, or consumer fencing with generation IDs.

H: What's the difference between consumer-side and broker-side deduplication?

A: Broker-side: broker tracks message IDs, rejects duplicates on publish. Simpler for producers, broker bears storage cost. Consumer-side: consumer tracks processed IDs, handles duplicates. More flexible, consumer controls exactly-once boundary. Often need both for end-to-end guarantees.
