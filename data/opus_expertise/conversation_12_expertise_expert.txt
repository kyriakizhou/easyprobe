HUMAN: I'm implementing a distributed rate limiter for our API gateway that needs to handle 100K requests/second across multiple regions. What algorithm and architecture would you recommend?

A: At that scale, exact consistency is impractical - network latency between regions makes synchronous coordination too slow. Consider a hierarchical approach: local rate limiting per region with periodic synchronization, or probabilistic counting using algorithms like HyperLogLog. Token bucket with eventual consistency is common.

H: We're using Redis. Currently a single Redis instance is becoming a bottleneck at 50K req/s.

A: Redis can handle more with pipelining and proper connection pooling, but for 100K+ with low latency, you need distribution. Options: Redis Cluster with keyspace sharding by user ID, or local Redis per region with async replication. Consider: is exact rate limiting required, or is approximate acceptable?

H: Approximate is fine - we're protecting against abuse, not billing. A user slightly exceeding their limit temporarily is acceptable.

A: Then use local sliding window counters with lazy synchronization. Each region maintains its own counter, periodically shares deltas with others. Total rate = sum of all regions. Accept that during sync intervals, global rate may temporarily exceed limit by (regions - 1) * local_limit. Usually acceptable for abuse prevention.

H: How do I implement the local sliding window efficiently?

A: Redis sorted sets with timestamps work well: ZADD for each request, ZREMRANGEBYSCORE to expire old entries, ZCARD for count. For higher performance, use a Lua script combining these atomically. Or implement fixed window counters with two keys (current and previous window) and interpolate.

H: What about the synchronization mechanism between regions?

A: Pub/sub for real-time updates is overkill for approximate limiting. Simpler: each region publishes its delta to a shared store (DynamoDB Global Tables, or a simple HTTP endpoint) every N seconds. On read, sum recent deltas from all regions. Stale data is acceptable.

H: How do we handle a region going offline?

A: Continue with local limiting. Use last known values from the offline region with time-based decay. If region is offline for too long, assume its contribution is zero. Alert on region offline. Consider: should offline region be more permissive or restrictive? Usually permissive is safer.
