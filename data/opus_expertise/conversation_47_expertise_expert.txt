HUMAN: We're implementing a custom authorization system using Zanzibar-style relationship-based access control. How do we efficiently check permissions through complex relationship graphs?

A: Zanzibar-style auth involves checking relationship tuples: (user:alice, viewer, doc:readme). Permission checks traverse relationships: user→group→folder→document. Challenges: graph traversal latency, recursive relationships, and consistency during relationship changes.

H: How do we handle deeply nested permissions without timeout?

A: Set traversal depth limits. Cache intermediate results aggressively. Use materialized permission sets for hot resources. Consider: check cache (expanded permissions) → if miss, traverse → cache result. Async background expansion for frequently accessed resources.

H: The relationship graph changes frequently. How do we handle cache invalidation?

A: Watch-based invalidation. When relationship changes, invalidate cached permissions that might be affected. This requires tracking: which cached entries depend on which relationships. Alternative: short TTL caching with eventual consistency.

H: How do we make permission checks fast for read-heavy workloads?

A: Pre-computed "check" indexes. For each (object, permission), store the set of subjects who have that permission. Query becomes set membership test. Trade-off: index update cost on relationship changes. Google's Zanzibar uses this with careful index management.

H: What about consistency? A permission grant should be immediately effective.

A: Zanzibar concept: "zookie" - a token representing a consistent snapshot. Reads specify minimum zookie, ensuring they see all changes before that point. For real-time needs: synchronous index update in the write path, then return zookie that includes the write.

H: How do we test authorization rules? They're complex and bugs are security-critical.

A: Unit tests for rule evaluation. Integration tests with known relationship graph and expected permissions. Property-based testing: generate random graphs and users, verify invariants (admin always has access, removed user never has access). Audit logging for production verification.
