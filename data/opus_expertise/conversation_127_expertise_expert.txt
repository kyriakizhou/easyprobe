HUMAN: We're implementing a real-time collaboration system. How do we handle operational transformation vs CRDTs?

A: OT: transform operations based on concurrent operations, centralized server determines operation order. CRDTs: data structures that merge automatically without coordination. OT: more complex algorithms but smaller messages. CRDTs: simpler conceptually but potentially larger state. Both solve same problem differently.

H: When would we choose OT over CRDTs?

A: OT better when: centralized server exists anyway (Google Docs model), operation size matters (OT transforms, CRDT needs full state sometimes), or need precise intention preservation. CRDT better when: fully peer-to-peer, offline-first, simpler implementation acceptable.

H: What are the challenges with implementing OT correctly?

A: Transform function must handle all operation pairs. Correctness properties: convergence (all clients reach same state) and intention preservation (operations do what user intended). Many published OT algorithms have bugs. Complexity explodes with operation types. Use proven implementations.

H: How do CRDTs handle text editing specifically?

A: Sequence CRDTs: each character has unique ID, position determined by predecessor/successor IDs. Concurrent inserts at same position: deterministic tiebreaker (compare IDs). Deletions: tombstones. Challenge: tombstone accumulation, especially in heavily edited documents.

H: What about undo/redo in collaborative editing?

A: Local undo: undo my operations only (preserve others' work). Challenge: my operation might have been transformed. OT approach: reverse transform, apply inverse. CRDT approach: depends on CRDT type, some support operation tombstoning. Often: accept imperfect undo in collaborative context.
