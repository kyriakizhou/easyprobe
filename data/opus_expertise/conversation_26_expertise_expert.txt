HUMAN: We're implementing a feature flag system that needs to handle millions of flag evaluations per second with sub-millisecond latency. How do we architect this?

A: At that scale, centralized evaluation is too slow. Distribute flag configuration to edge: embed SDK with local evaluation, sync configuration periodically or via push. Evaluation happens in-process with no network call. Configuration updates propagate eventually.

H: How do we push configuration updates quickly to thousands of SDK instances?

A: Pub/sub pattern. Central service publishes config changes. SDKs subscribe. Technologies: Redis pub/sub, Kafka, or specialized systems like LaunchDarkly's streaming. Also support polling fallback if push fails. Include config version for consistency checking.

H: What about consistency? User might see different flag values across requests during rollout.

A: Accept eventual consistency for non-critical flags. For critical flags needing strong consistency, use deterministic hashing: hash(user_id + flag_name) determines bucket, config specifies bucket percentages. Same user always gets same value regardless of which server evaluates.

H: How do we implement percentage rollouts with deterministic assignment?

A: Hash user ID to value 0-99. If rollout is 30%, users with hash < 30 get new experience. Increase to 50%, users 0-49 now included. Same users, expanding set. Use consistent hashing algorithm (murmur3) for even distribution. Include flag name in hash for independent flag randomization.

H: We need targeting rules - flag on for specific users, companies, or attributes.

A: Evaluate rules in order: explicit user overrides first, then segment rules, then percentage rollout as default. Rule format: {attribute: "company_id", operator: "in", values: ["acme", "globex"]}. Keep rules simple for evaluation performance. Complex rules evaluated locally against user context.

H: How do we test flag changes before global rollout?

A: Multiple environments in config. SDK configured with environment (dev, staging, prod). Changes tested in lower environments first. For production testing, target internal users or specific companies first. Feature flag systems themselves need staged rollout.
